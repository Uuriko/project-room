## 3. What fantastic means

A deploy is a labelled, attributable, reversible fact — never a rumour the fleet reconstructs afterwards. Concretely, from the dispatcher's seat and from any reader of the record:

- **Honest label, always.** The run's headline outcome separates the two facts: `PUBLISHED` (both Workers live on the dispatched SHA + build-id) and `SMOKE` (passed / failed / not run). A run in which both Workers published is never summarised, in the run conclusion, the muse-room receipt, or the step summary, by the single word "failure". Reader test: from the receipt line alone, a person who was asleep can tell whether production changed.
- **Fast truth.** Dispatch → verified-live ≤ ~120 s typical (publish ~21 s + one bounded smoke in the ~90 s class #5111 budgets; no fixed sleeps anywhere in the path). A genuinely broken build is declared failed and recovered within ≤ ~300 s wall, not 841 s.
- **One publisher at a time, mechanically.** Overlapping publishes of deploy-prod and rollback-prod are impossible — refused before the first wrangler publish, not merely queued by a concurrency-group declaration that 2026-10-27 proved insufficient on its own. Two dispatches in the same minute produce one publish and one explicit, early refusal/queue, zero interleaved publishes.
- **No unvetted build ever touches production (end state, Phase 2).** The artefact is built once, smoked against the staging script, and the *same* Worker version is promoted to both production doors. Bad-day shape: one rejected staging promotion, zero production flips, zero door divergence. Rollback is a version re-point of a bit-identical artefact: ≤ 60 s end-to-end, no rebuild, no republish cycle.
- **Every flip has a contemporaneous record.** 100% of served-revision flips (deploys and rollbacks, workflow and any surviving direct route) have a DEPLOY_RECORD written in the same act — same run, or within one deploy-watch poll cycle for a route that cannot write its own — naming target SHA, build-id, both Worker version ids (new + rollback target), actor, reason, run URL, and publish/smoke outcomes separately. The 14-day rolling count of contemporaneous records equals the 14-day flip count; the W7 census re-run (§5) reports 0 stubs-as-only-record and 0 `UNRECOVERABLE` actor fields for workflow deploys.
- **Attribution that cannot be forged (once armed).** After John's key-custody step, every record carries an ed25519 signature over {buildId | sourceRevision | actor | at}; deploy-watch verifies against a named-seat keyring. A flip with no record raises `ALARM-UNRECORDED`; a bad signature raises `ALARM-BAD-SIGNATURE` (claimed actor shown as UNVERIFIED, never as the actor); only a valid signature yields `OK-SIGNED`. Target, from the E3 replay: 3/3 non-compliant flips alarmed, 0 false alarms, compliant-deploy attribution 100%.
- **The runbook tells the truth.** `docs/DEPLOY-LANE.md` describes the pipeline as it actually behaves after each phase (label semantics, promotion, record + alarm states), and the two shelf checks (Board stocked, gallery fresh) remain the last gate before a deploy is called done.

Exemplars worth matching: the repo's own receipt discipline elsewhere in the product (a receipt names what happened, not what was attempted); GitHub Actions' own job/step separation (publish and verify as separately-named conclusions); Cloudflare Workers Versions' model (deploy = traffic/version re-point of an immutable artefact — the Phase 2 target shape).
