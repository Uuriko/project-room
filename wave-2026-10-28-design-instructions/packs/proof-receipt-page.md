## 3. What fantastic means

A stranger who receives only this link can, **without an account, without trusting the server's word alone, and in under two minutes**, answer: what record is this, what has actually been checked (and by whom — server, platform, or nobody yet), and is this exact record inside the room's published set, unaltered since that set's root was computed?

Concrete end state, all measurable:

- **Inclusion in ≤2 clicks, ≤2 KB.** From the detail page: one click downloads the receipt's proof JSON — leaf, index, epoch, root, sibling path — **≤2,048 bytes** for any receipt in a full 1,000-leaf epoch (path ≤10 hashes at `EPOCH_SIZE = 1000`; B1's 14-hash / 1,078-byte figure is the 10,000-leaf corpus shape). A second click reaches copy-paste offline verification instructions that need only the proof JSON and a stock `node` (or any sha256 tool) — **no repo checkout, no log, no account**.
- **Verify cost stays the measured win.** Server-side proof generation + `verifyProof` for a mid-epoch receipt measures **<1,000 µs** at acceptance on a 1,000-leaf epoch (charter kill line), against the B1 headline of 10.04 µs vs the chain's 7,873.5 µs at 10,000 leaves.
- **The chain is visible, not just asserted.** On a lot receipt, every journal entry for the lot is listed in seq order with its hash and its link to the previous entry, labelled in words ("Stored chain — not re-hashed on this view" by default; after `?verify=1`, the re-hash verdict and the entry count it covered). A broken link, if a verify run finds one, is named by entry id — never smoothed into a generic failure.
- **No raw-hex-only evidence.** Every hash on the page is either (a) labelled with what it is a hash *of*, or (b) explicitly labelled "Stored hash — the record does not name what this covers". The verification and inclusion blocks never ask a reader to compare hex by eye (the existing renderer's rule, kept).
- **Zero claim upgrades.** The inclusion block's strongest sentence is inclusion + tamper-evidence relative to an **unsigned** root, printed next to what it does not prove (not acceptance, not payment, not identity, not a signature) — in the same block, not a footer. Copy tests pin this (§5).
- **Page character unchanged.** Script-free HTML (no `<script>` added — offline verification happens *off* the page, from the downloaded JSON), `no-store`, detail HTML grows by **≤3 KB** over its per-shape baseline (≈10.8 KB for the probed `pwr_` shape), and the block renders within the existing 42rem single column at mobile width without horizontal scroll (long hashes wrap, as today).
- **Exemplars worth matching:** Certificate Transparency's inclusion-proof presentation (RFC 6962: leaf + audit path + signed tree head, with the trust in the head stated separately from the inclusion math) and Sigstore Rekor's inclusion-proof display (proof downloadable as JSON, verification runnable independently of the log operator). Match their separation — *inclusion is math; the root's authority is a separate, named trust step* — not their signing claims, which this product cannot make today.
