## 1. The piece

Presence is the system's answer to three questions, and it is three different mechanisms — do not conflate them:

| Question | Mechanism at main `aaa749065a` (verified in the archive tree) | Key semantics |
|---|---|---|
| Who is in the room, and what are they doing? | `RoomStore.presence()` / `presenceMembers(roomId, watcherMemberIds)` in `server/store.mjs` (~L5063–5173). Per member: `memberId, displayName, kind, watching, workingOn, lastSeenAt, statusMessage, presence{status,lastSeenAt}, state, isOwner, scopes, ownerIdentityId, cardAgentId` | `watching` = live SSE stream for that room (computed in `server/http.mjs` from the `streams` set, passed in at the legacy `GET …/presence` handler ~L4740 — a duplicate handler exists ~L4541); `workingOn` = fresh `processing`/`active` work-item sessions from the projection; `state` from `presenceState()` in `src/presence-state.js` |
| When were they last seen? (`lastSeenAt`) | `lastSeenAt = max(latest command event `at`, session heartbeat `heartbeat_at`, enrollment `member.added` `at`)`, per member. At main the first and third terms are **recomputed on every read** by two full event-table scans: `server/store.mjs:5106` (`max(json_extract(body,'$.at')) … GROUP BY actor`) and `:5110` (`MIN(…)` over `member.added`). Session heartbeats come from work-item session records, stale after `SESSION_HEARTBEAT_STALE_MS` = 10 min (`src/work-item-session.js:29`) | All freshness is a **read-time** computation over those timestamps: `presenceState()` windows in `src/presence-state.js` — live/listening 5 min (`PRESENCE_LIVE_WINDOW_MS`), idle 60 min, unreachable 60 min; states are exactly `working / listening / idle / unreachable / unknown`. Presentation only, never an authorisation or lease rule (file header, `src/presence-state.js`) |
| Is an agent's host alive? (heartbeat) | `server/agent-heartbeats.mjs`: `POST /api/agent-heartbeats` upserts `agent_hosts` (one row per agent+host, `last_seen_at`); `AgentHeartbeats.statusOf(identityId)` returns `online / offline / unregistered`. Reachability window = `max(180 s, cadenceSeconds × 1.5)` (`HEARTBEAT_STALE_AFTER_MS = 180000`, server-assigned cadence, default 120 s). At main `presenceMembers()` and `capabilities()` call `statusOf()` **per agent member** (presence calls the host derivation twice per member via `hostStatusOf` + `agentPresence`) — the N+1 leg | `presenceMembers()` maps `unregistered` → `status: null` (RC-051 contract: roster still lists the member, no presence field); `capabilities()` keeps the raw status including `"unregistered"` |

## 3. What fantastic means

Presence feels instant, costs nothing as rooms grow, and never lies about freshness:

- **Read cost flat vs history (Track A landed):** the presence derivation (`_memberActivityMaps` at #5133's head) measures **≈0.1 ms flat at 200 / 1k / 5k / 20k events** (0.10 / 0.13 / 0.10 / 0.09 ms, PRES §3), vs 173 ms p50 at 20k today. `store.presence()` p50 in the same harness: **≤12 ms at 20k events** (was 173 ms), with **zero event-count slope** — a 20k-event room and a 200-event room differ only by fixed roster/projection work. Host status is a constant number of queries per read (one chunked hosts query + one chunked cadences query per roster), not 2 per agent member.
- **Semantics byte-identical:** for an identical event script, `presence()`, `capabilities()`, `staleMembers()` and `agentPresence()` outputs are byte-identical before/after at every clock point, including the window edges (live 5 min −1 ms / exactly-at / +1 ms; 60-min points; host window 180 s −1 ms / at / +1 ms) — the standard PRES-CRITIC's differential probe already set. `lastSeenAt` still means max(command, session heartbeat, enrollment); no window, state name, or RC-051 null mapping changes.
- **Freshness a human can see (Track B landed):** a member joining, leaving, or changing awareness state is visible to other clients with **staleness p95 ≤50% of the 1 s polling baseline** on the production-shaped bench at 200 and 500 clients (H3 spike reference: 237 ms / 160 ms vs 2,094 ms / 1,932 ms), at **bytes/client/min ≤70% of polling** (spike: 40,741 / 55,078 vs 172,088 / 179,407). The 30 s full-state poll is gone for WS-connected clients; it survives only as the fallback.
- **Presence never becomes data:** join/leave/awareness churn for 60 s changes the room's event count by **0** and its projection byte size by **0** — presence state is ephemeral, held outside the event fold and outside the 4 MiB per-room projection, exactly like typing beats today.
- **Stale is labelled stale:** when neither WS nor a poll has refreshed within 60 s, the roster says so ("Availability needs refresh" class copy already in `src/app.js`) — presence never renders a cached report as current. That honesty, plus the five state words, is the whole user-visible vocabulary; no new states are introduced.
- **Exemplars to match:** the awareness pattern from PartyKit (ephemeral per-connection state, broadcast on change, heartbeat + terminate-dead — pattern only, per H3); the in-repo typing indicator (ephemeral, TTL-expired, synthetic stream events, zero persistence) as the local precedent for "live but not data".
