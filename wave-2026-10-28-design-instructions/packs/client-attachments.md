## 1. The piece

### Correction to the charter premise — read this first

The H4 discovery lane reported "rooms have no attachment pipeline at all; the only in-product place bytes could go is the event log" (`~/workspace/wave-2026-10-27-discovery-50/lanes/H4/REPORT.md`, Baseline). **That premise does not hold at `aaa749065a`.** Verified in source: a complete small-file pipeline already exists — staged/commit room files over REST and MCP, a browser composer, and a download-with-sha256-check client path. What does not exist is everything above **1 MiB**: no chunking, no streaming, no content dedupe, no resumability, no media preview, and transport is whole-file canonical base64 inside JSON on every door. This pack therefore instructs **extending the existing pipeline past 1 MiB**, not building a parallel one. The charter's end-state, price ceiling (20 lh budget kill), falsifier, and acceptance shape stand unchanged; its "new, separate store" wording (§6) is superseded by §4 step 1 of this pack — a second blob store beside `room_attachments` is an explicit non-goal.

**Broken / degraded / missing at `aaa749065a` (verified in source, §1):**
1. **1 MiB hard ceiling on every door.** Client refuses pre-request (`src/app.js`, `src/composer-files.js`), server refuses with 413, HTTP body cap is 1,406,296 B, MCP contract says 1 MiB. An ordinary phone photo, a short screen recording, most PDFs with images — all refused, everywhere, with no alternative path.
2. **Whole-file base64-in-JSON transport.** Every upload and download carries the file as one base64 string (+33% bytes) and materialises it whole in memory on both sides (client `btoa` over the full buffer; server one `Buffer.from`). Even if `fileBytes` were merely raised, this dies next at the SQLite single-value limit (§1 topology) — the ceiling is architectural, not a constant.
3. **No resumability, no progress.** Upload is a single shot; the chip says "Uploading …" with no percentage; any failure discards all progress and the retry restarts from byte 0 (`retryComposerFile`); after a reload the draft keeps the chip but the user must reselect the file.
4. **No content dedupe.** Identical bytes under two client ids are stored twice in full; dedupe exists only for an exact id replay. (Spike: 40% saving on a duplicated corpus.)
5. **No signed retrieval.** Downloads are authenticated-session/bearer JSON only. There is no expiring, tamper-evident retrieval token of the H4 spike's shape, and no raw/binary download route at all — the browser must base64-decode and hash in JS before it can save anything.
6. **Display is a filename.** Committed files render as filename-only chips: no size, no type, **no image preview of any kind** (an attached screenshot — the commonest room attachment — must be downloaded and opened elsewhere), and download forces `application/octet-stream` regardless of the stored media type.
7. **Room quota is 16 MiB total** (`roomBytes`), 8 MiB per member — sized for the 1 MiB era. At any larger per-file limit this quota, not the file limit, becomes the refusal users hit, and its error (`attachment_quota`, 409) does not say which quota or how much room is left.
8. **Peer visibility lag.** Commit appends no room event, so other members see a file only after the 1.2 s / 5 s heuristic re-reads in `refreshRoomFiles()` — a known, accepted wart today; §4 keeps it out of scope but forbids making it worse.
9. **UNVERIFIED:** no UT1/UT2 journey on file exercises an attachment over 1 MiB, an image attachment, or a failed-upload resume; there is no executed user evidence for this surface beyond the browser check scripts in-repo (`scripts/composer-browser-check.mjs`, `scripts/composer-live-files-browser-check.mjs`, `scripts/auth-return-browser-check.mjs`). Do not cite UT for this piece.

## 3. What fantastic means

The user-visible end state, with the numbers that prove it:

- **A 50 MiB file just works.** A member drags a 50 MiB video (or a 5 MiB phone photo) into the composer and it attaches; a peer downloads it byte-identical. Per-file ceiling **50 MiB (52,428,800 B)**, stated in one limits line in the composer and in `docs/openapi.yaml` — nobody discovers a limit by hitting it (closes the EXP-8/#4451 complaint for this surface).
- **Chunked, resumable, honest upload.** Upload moves in **256 KiB chunks** (the spike's size); the chip shows a real percentage; a dropped connection or a page reload resumes from the server-acknowledged chunk count with **at most 1 chunk retransmitted**; an over-limit or blocked-type file is refused **before the first byte is sent** (client pre-check on `file.size` + type, zero upload requests issued), with one sentence naming the limit and the file's actual size.
- **Bytes never touch the projection.** After attaching 50 MiB + 5 MiB, the room's projection byte count and event count move only by the small attachment-reference records (charter §8 check 2: growth attributable to payload = fail; reference-record growth is a few hundred bytes per file, never kilobytes).
- **Dedupe is real.** Attaching the same bytes twice in a room stores them once: second attach completes as a dedupe hit and stored blob bytes increase by **0**.
- **Retrieval is signed, expiring, and binary.** Downloads stream raw bytes (no +33% base64, no whole-file JS decode); retrieval tokens are HMAC-signed with **≤15 min expiry**; an expired token and a token with one flipped signature character are both refused; sha256 is still verified end-to-end (the client keeps its hash check on the assembled bytes).
- **Display shows the file.** A committed image (png/jpeg/gif/webp/avif) renders an inline preview in the message (auto-preview ≤10 MiB; larger images show the chip plus an explicit preview action); every other file's chip shows filename + human-readable size + media type, and download uses the stored media type. Screen-reader labels stay at least as good as today's (`file.download.action` pattern).
- **Quotas sized for the new ceiling, and legible.** Defaults set by this pack (config constants, not magic numbers in code): file 52,428,800 B; member 268,435,456 B (256 MiB); room 1,073,741,824 B (1 GiB) counting **unique stored bytes per room**; staged lifetime stays 24 h; ≤20 files per message stays. A quota refusal names the quota hit and the bytes remaining.
- **Speed floor, not spike promise:** on the acceptance harness the 50 MiB round trip completes at **≥10 MB/s end-to-end** with the wall time filed (the spike's 122–176 MB/s was local filesystem; chunked SQLite will be slower and that is fine if the floor holds). Sending a text-only message is unchanged: 0 added requests, 0 added latency.
- **Exemplar worth matching (web-checked 2026-10-28):** Slack's help page for adding files — files up to 1 GB, drag-and-drop into the composer, inline preview for images, and a sequenced multi-step upload API (`getUploadURLExternal` → upload → `completeUploadExternal`). Match that **shape** (sequenced upload + preview + stated limits), not its 1 GB ceiling; 50 MiB is this product's chartered number.

No John's-decision fork is touched: the download hash check is file integrity, and UI copy must not call an attachment "verified" in the receipt sense — that vocabulary is fork (a), pending, and this piece stays out of it. Sponsor surfaces (fork b) are untouched.

**Step 2 — Server transport: chunked upload sessions + signed raw retrieval.**
- New REST routes, in `server/http.mjs` beside the existing room-file regex routes, with the same credential/scope/guest/autonomy-tier enforcement as the existing stage route (reuse, don't re-implement — the guest denial and tier checks live in the store layer):

Re-POSTing the same index with identical bytes is a duplicate success; different bytes at an acknowledged index → new code `attachment_chunk_conflict` (409). Response returns the count of acknowledged chunks (the resume cursor).
  3. `POST /api/rooms/:roomId/files/uploads/:id/complete` — server assembles the chunk hashes, verifies total length and the declared sha256; mismatch → `422 attachment_hash_mismatch`, chunks purged, no reference row committed. ## 5. Acceptance

The coordinator/Jill runs these at the exact landing head (single landing, §4). The first five are the charter's §8 checks, adapted to the shipped paths:

1. **50 MB round-trip:** generate a fresh 50 MB random file, upload it through the shipped chunked path (browser composer or the REST session routes), commit it onto a message, download it via a minted raw token, compare sha256 — identical; the hash pair and the end-to-end wall time (floor ≥10 MB/s, §3) are filed with the acceptance record. Repeat at 5 MiB.
2. **Projection invariant:** record the test room's projection byte length (`LENGTH(projection)` via the store) and event count before and after the 50 MiB + 5 MiB attachments: both unchanged except the attachment-reference records; any growth attributable to payload bytes fails acceptance and triggers the charter's cap kill.
3. **Dedupe check:** attach the same 1 MiB payload twice under different names/ids in one room — total stored chunk bytes increase only once; the second complete reports a dedupe hit.
4. **Token check:** an expired token and a token with one flipped signature character are both refused on the raw route; a valid token succeeds; a token minted for member A does not retrieve a DM-committed file A cannot see (visibility still enforced at mint).
