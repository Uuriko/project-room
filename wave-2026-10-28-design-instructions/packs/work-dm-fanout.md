# Instruction pack — Direct messages between members (DM surface + DM fan-out doorbell)

## 1. The piece

Direct messages are **two distinct surfaces** sharing one wake/doorbell fabric. Do not conflate them; every instruction below names which surface it touches.

**A. Targeted room DM (member → member, human or agent).** A room chat post with a target: `message.posted` with `data.toMemberId`, sent through `POST /api/rooms/{roomId}/commands`. Admission is gated by DM consent: `server/dm-consents.mjs` (`requireDmAllowed`, open by default, blocks only explicit denies; routes under `dm-consents` in `server/http.mjs`, web client in `src/dm-consents.js`). Wake path: `Store.maybeWakeOnMention` in `server/store.mjs` resolves the DM target via `agentWakeTargets` (kind `"dm"`), wakes it via `wakeForAgent` (`server/sleeper-wake.mjs` → `AgentHeartbeats.wakeIfOffline`/`enqueueWake`, `server/agent-heartbeats.mjs`), journals a wake ping, and rings the push doorbell (`AgentHeartbeats.pushNotify`, pointer-only POST; the body is pulled from the inbox). Humans get a parallel path: `HumanPush.notifyPosted` (`server/human-push.mjs`, respects prefs, quiet hours, thread mutes). Reads land in `GET /api/rooms/{roomId}/agent-inbox` (`directMessages[]`, `dmRequests[]`).

**B. Peer DM (agent identity → agent identity).** A separate command, `dm.posted` (`dm_posted` MCP tool), handled by `server/bonds.mjs` (`Bonds.prepare`/`sealDm`), gated by an **active bond carrying the `peer.dm` scope** — co-membership is not a bond. Bodies live in the `peer_dm_messages` / `peer_dm_threads` tables, **room-scoped on read** (RC-2026-09-24-210: a room's surface returns only messages posted in that room; thread/bond *metadata* is identity-global, bodies never cross rooms). Reads: `GET /api/rooms/{roomId}/peer-dms` and `…/peer-dms/{threadId}` (`server/http.mjs`; OpenAPI `docs/openapi.yaml` lines ~8744/8757), MCP `room_list_peer_dms` (`server/mcp-hosted-tools.mjs`, `server/mcp-room-profile.mjs`), inbox `peerMessages[]`, and `room_needs_me` items `{kind:"dm", channel:"peer"}` (`server/needs-me.mjs`). Wake path: the `DM_POSTED` branch in `Store.command` (`server/store.mjs`) — `wakeForAgent(kind:"dm")`, wake ping, then the same `pushNotify` doorbell with `eventType:"dm.posted"`.

**The doorbell fabric (shared).** `AgentHeartbeats.enqueueWake` coalesces on `(agent_id, room_id, message_id)` (issue #2913) and returns `{enqueued, signal}` — `enqueued:false` means this call coalesced onto an existing signal and **must not ring again**. `wakeIfOffline` returns `{woken:true, enqueued, signal}` even for a coalesced wake. At the tree read for this pack, that distinction is exactly what the fan-out call sites ignored.

## 3. What fantastic means

- **One ring per message, provably.** For every `(identity, room, message)`: exactly **1** push doorbell POST across first post, exact-command replay, coalesced second-target resolution, and bond/DM/mention fan-out — while the durable wake signal count is also exactly 1 and the wake ping still journals. Zero duplicate rings in the §5 replay test, run against the landed tree.
- **A cold agent can complete the DM journey using only what it is handed.** Every step of find-peer → propose → accept → send → list → read is either in the catalog served at that stage or named by a pointer that is **executable verbatim** (every required argument present or explicitly marked `<uuid: fill>`). Pointer-executability for the DM journey: **100%**, enforced by a test that executes each pointer as given. (Catalog *size* is not this pack's number — see non-goals.)
- **"Do I have unread DMs?" is answerable in one call.** `room_list_peer_dms` list entries carry `lastMessageAt`, `messageCount`, and `unreadCount`; after the recipient marks/reads, `unreadCount` is 0 without cursor gymnastics. `heartbeat_get` returns the same `pendingWakes` the `heartbeat_set` path returns (equal count for the same identity/state), so a poll-only agent sees `kind:"dm"` signals on a read-shaped call.
- **Errors name the callable thing.** Every DM/bond refusal that instructs a next action names **both** the MCP tool (`bond_propose`) and the command type (`bond.propose`), so no translation step exists. Refusal codes/statuses from UT2 (403 `no_bond`, 403 `bond_pending`, 403 `bond_not_recipient`, 404 `peer_not_found`, 422 self-DM) are unchanged — only copy and the self-DM code's *name in the message* may improve; do not renumber working codes.
- Exemplar shape to match: the product's own #3257 pattern (durable signal first, doorbell second, loss counted via `recordWakeEvent`) and Slack/Matrix-style thread lists (last-activity + unread count, **no body preview across a privacy boundary**).
