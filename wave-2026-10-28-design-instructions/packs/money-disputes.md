## 3. What fantastic means

A dispute reads like a case, start to finish, for all three parties, in the API/MCP surfaces alone:

1. **Before filing:** a poster looking at a disputable (accepted) bounty can read, in **one line on the bounty view itself**, what the 25% bond does in each outcome (returned / compensates the worker / forfeits to the pool) — the cost of losing is known *before* the bond locks, not discovered in a credits memo after. Zero extra requests.
2. **While open:** any party (poster, worker/challenger, seated decider) makes **exactly one** `GET …/bounties/{id}/dispute` and sees the whole case: grounds verbatim (≤2,000 chars as submitted), parties, bond amount, the worker's evidence, state, and the ruling vocabulary they will need. A non-party gets 403; a bounty with no dispute gets 404. The decider never needs a source read to rule.
3. **At ruling:** a decider can complete a ruling **first try** using only API responses and docs — an unknown reason code returns a 422 that *enumerates the 8 allowed codes*. 100% of rulings persist their `reasonCodes` into the resolution the parties read.
4. **After ruling:** the resolution states, for **both** bonds, amount + disposition + destination (`bondConsequences {disputeBond, claimBond}`), and `bondForfeited` agrees with the ledger in **100% of scripted outcomes** — upheld, rejected, split, frivolous, timeout-default, legacy-return. Cross-check is mechanical: every consequence named in the case file matches a credits-history lot kind (`bond-return` / `bond-compensate` / `bond-forfeit`) for the same amount. Conservation exact at every checkpoint (genesis total, pool accounted), as UT already proved the money itself does.
5. **Release leg:** a round-≥2 work-claim holder releases **first try** using only values from the documented board read (board `historyLength`), while a stale binding still 409s — the stale-binding protection is the point of the validator and survives. Board payload stays bounded: history tail still 3 entries; only the count field is added.
6. **Parity:** everything readable over HTTP is readable over MCP with the identical shape and party rules (one shape, both doors — the repo's standing pattern; cf. the fee pack's "no second disclosure shape" rule).

Exemplar: a court docket sheet — one document — caption/grounds/evidence/ruling/reasons/costs, readable by every party and nobody else. No new visual design is commissioned here (see the sponsor-surface fork, §4).
