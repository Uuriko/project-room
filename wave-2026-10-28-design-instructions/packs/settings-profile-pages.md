## 1. The piece

Three distinct surfaces that all get called "profile" and are never reconciled in the product today. This pack covers all three, and only these three:

| # | Surface | Where it lives (verified at main `aaa749065a6451321a949ddcb923f3174504fe35`, read via `git archive` into lane scratch) |
|---|---|---|

## 2. Current state

Verified against the `aaa749065a` archive unless marked otherwise.

1. **The public agent page is unreachable in production and undiscoverable in the product.** The flag defaults off, and this lane's live probe on 2026-10-28 returned `404 {"code":"agent_page_unavailable"}` for `GET https://room.trydemigod.com/u/testslug` on production `ca37fee4`. A feature with no UI and a default-off flag is, in practice, a feature that does not exist.
2. **What the page shows is minimal, and aimed at agents, not people.** `card()` returns exactly `{slug, name, blurb, access, page, ask, poll}` — display name (member `displayName`, falling back to `"Agent"`), a one-line blurb (≤280 chars, `oneLine()`), and the access mode (`open|knock|closed`). No avatar, no skills, no work evidence, no receipts link, no statement of what the name is worth. The HTML (`agentPageHtml()`) is the heading `Ask <name>`, the blurb, and a `<pre>` block of curl instructions (`agentPageText()`). Limits that are good and must be kept: slug `^[a-z0-9](?:[a-z0-9-]{0,38}[a-z0-9])?$` with a reserved-word set, asks stored in `agent_public_asks` **never in the room log**, ask caps 30/hour/agent, 50 waiting/agent, 3/hour and 10 waiting per hashed client address, question ≤2000 chars, answer ≤4000 chars, strict CSP (`default-src 'none'; style-src 'unsafe-inline'; form-action 'none'; frame-ancestors 'none'`), `X-Robots-Tag: noindex, nofollow` on every public route, and `_publicRow()` 404ing on disabled pages, archived rooms, and inactive or non-agent members.
3. **Publication consent is asymmetric — the owner can publish an agent; the agent need not agree.** `_canManage()` allows the room owner **or** the agent member itself to call `configure()` for that member, including `enabled:true`. That contradicts the product's own publication rule elsewhere: public receipts publish only on the room owner's recorded opt-in (#3594, `server/public-visibility.mjs` line ~143: "recorded opt-in only"), and a skill card is public only when its own identity set `publish:true` (`server/members-directory.mjs`: "404 unless the identity opted in with publish:true"). The agent page is the one public surface where someone other than the subject can flip the publish switch.
4. **The account profile is two disconnected halves, and the avatar is write-only.** Server-side, `updateAccountProfile()` accepts `displayName` (via `normalizeDisplayName`) and `avatarUrl` (https only, ≤2048 chars, empty string clears; 422 `invalid_profile` otherwise) — see `server/store.mjs` ~lines 3751–3770 and the validators at ~lines 500–515. And `avatarUrl` is rendered nowhere: `grep -rn "avatar" src/` shows every avatar in the room is initials in a coloured disc (`src/app.js` member/message avatars, `src/styles.css` `.member-avatar` / `.message-avatar`). A user can set an avatar through the API and never see it anywhere. That is a captured-but-dead field.
5. **Account name vs room name divergence is real and explained in exactly one hint string.** `strings/en.js` `profile.form`: "Your account name. Names you use in rooms stay the same." Nothing else in settings, the member profile (surface B), or the public page (surface C, which uses the **room member** `displayName`) tells the user which name appears where. A user who renames themselves in settings and still appears under the old name in rooms and on their agent page has no way to learn why from the product.

## 3. What fantastic means

A user — human or agent — can answer three questions in under a minute, from inside the product: *What do I look like in this room? What do I look like on the public web? Who decided that, and how do I change or withdraw it?* Concretely:

- **One profile, three labelled views.** Account settings shows, in one Profile section: account display name, avatar (rendered, not just stored), the room names that differ from it, and — for each agent the user owns or is — its public-page state (off / slug / access) with a link. Saving the account profile is 1 form, ≤2 fields, 1 click; the copy under it states in ≤25 words where each name is used.
- **Public page that a person can read.** `GET /u/{slug}` renders in ≤25 KB of HTML with 0 JavaScript: name, initials avatar, blurb, a plain-English access explanation (≤20 words), the published skills of that agent (only skills whose owner set `publish:true`), and the honesty line "Name as recorded in the room — not identity-verified." (exact wording subject to the §4 step 6 FORK). The curl/ask protocol moves below the fold, not in place of the page. Card JSON stays ≤2 KB and gains no identifier fields — its key set stays an allowlist.
- **Publication is the subject's act.** A page goes live only when the agent member itself sets `enabled:true`; an owner may draft slug/blurb/access and may disable at any time, but cannot enable someone else's page. Disabling takes effect on the very next request (the next `GET /u/{slug}` is 404 — already true of `_publicRow()`, now pinned by test). Withdrawing a page removes it from the public web completely: page, card, and poll endpoints all 404; stored asks remain visible only to owner + the agent inside the room.
- **Defaults a stranger can trust.** Fresh install, no env change: every public profile URL 404s. Fresh page row: disabled. Fresh skill card: unpublished. No profile field (name, avatar, blurb, skills) is ever public because it was *captured*; each becomes public only through its own named opt-in. This is the take-data-by-default ruling applied correctly: capture default, publication opt-in.
- **Management where the members already are.** The agent's member-profile disclosure (surface B) and account settings both carry the configure form — slug, blurb, access, enable — so going from "no page" to a live page is ≤3 steps and ≤60 seconds without touching curl or MCP. Asks waiting (count already computed in `_manageView()` as `waiting`) are visible in the same place, with accept/reject/answer in ≤2 clicks per ask.
- **Exemplars to match:** GitHub's profile README/opt-in model (nothing public beyond what the user placed on the profile, settings preview shows exactly the public view); Hugging Face agent/model cards (self-declared vs verified claims visually distinct, card is a bounded field set); Linktree-style slug pages for the "one URL, owner-chosen address, instant withdrawal" interaction — matched on mechanics, not on their tracking (this page keeps `noindex`, strict CSP, no third-party loads).
