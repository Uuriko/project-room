# Instruction Pack — door-magic-recovery (magic / email recovery, end to end)

## 1. The piece

**What it is.** The passwordless way back into Project Room, plus its sibling password-reset-by-email. A stranger or returning user who cannot (or will not) present a password gets a single-use emailed proof, clicks it (or types the code), and lands signed in on a restored session — with any invitation/room context they started from intact. This pack covers four legs as one piece: **request → email → link/code redemption → session restore**, and the **401 gating** that controls when the offer exists at all.

Production is a different, older tree: build `ca37fee4` (pre-#5090, see §2) — **this pack targets main `aaa749065a`**; deploying it is the seat/operator's act, not the implementer's. **Routes (all POST, all in `server/routes/auth.mjs`, group `AUTH_ROUTES`, parity-exempt human-browser rows in `server/routes/table.mjs` via that file):**

| Route | Purpose | Key contract (source-verified) |
|---|---|---|
| `POST /api/auth/magic/request` | Issue sign-in code | Requires account-slot cookie + `Origin` + CSRF (`protectWrite`); no slot → 401 `account_session_required`. Body `{email, returnTo?}`. Answers `{status:"sent"}`, or 200 `{status:"unavailable", reason:"mail_not_configured"}` issuing nothing when no mailer. Response identical whether or not the email has an account. Rates: 5/min/address, 3/hour/email (`magicRequestEmailLimiter`, capacity 3, refill 3/3600 s, `server/http.mjs:450`). |
| `POST /api/auth/magic/consume` | Redeem code, sign slot in | Body `{email, code, sessionRevision}` (+ slot from cookie). Slot/CSRF verified **before** any code burns. Wrong/expired/consumed/5×-burnt → 401 `invalid_magic_code`. Slot already signed into a *different* account → 409 `magic_account_mismatch` **before** the code burns. Success → 201 `accountView`: account found-or-created as `email:<sha256hex>` (generation suffix after a deleted tombstone, max 20), magic method linked, slot rotated to a fresh token (old slot + any `room_session` cookie revoked). Rates: 10/min/address, 10/hour/email. |
| `POST /api/auth/password/reset/request` | Issue reset proof | Same slot/Origin/CSRF and uniform-answer discipline as magic request; 5/min/address, 3/hour/email. Proof purpose-bound, changes nothing on request. |
| `POST /api/auth/password/reset/consume` | Set new password from proof | Body `{email, code, newPassword (10–256), sessionRevision}`. Stale revision → 409 `stale_session_revision`; signed-in foreign account → 409 `reset_account_mismatch`, proof unburned in both. Success → 200 `{status:"password_reset", signInRequired:true}`: verifier changed atomically, target's human sessions/credentials revoked (`invalidateHumanAccountCredentials`), reset-complete notice mailed (notice failure cannot undo the reset), **no sign-in — user signs in fresh**. |
| `GET /api/auth/signin-options` | Capability feed | `server/routes/signin-options.mjs`; `providers.mail.configured` drives whether the client offers email recovery at all (§2). |

**Code store (`server/account-login-methods.mjs`, table `account_magic_codes`, hashed at rest — sha256 digest only).** `MAGIC_CODE_TTL_MS = 15 min`, `MAGIC_CODE_MAX_ATTEMPTS = 5` (5th miss deletes the live code). Magic code = 192-bit base64url (32 chars). A fresh request **deletes every prior unconsumed code for that email** — only the newest link is ever live. Reset digests additionally bind account id + `authEpoch` + current verifier, so a reset proof can never become a login and dies when the password changes. Consume claims the row atomically (`consumed_at IS NULL AND expires_at > now`) inside a transaction; miss counters commit before the 401 is raised.

**Mailer seam (`server/magic-links.mjs`, `server/resend-mailer.mjs`, wiring `server/boot-options.mjs` + `cloudflare/room.mjs:177-183`).** `createMagicLinkMailer({send, baseUrl})`; real sender is Resend (`RESEND_API_KEY`, `ROOM_MAGIC_FROM`, default From `Project Room <noreply@trydemigod.com>`), absent key → unconfigured seam, never a fake send. Link built by `buildMagicLinkUrl`: `?magic=<code>&email=<addr>` (or `?reset=…`), plus validated `returnTo` (strict local-only: `/` with only `room`/`account=1` query and `#invite/…`, `#join/…`, `#code/…` fragments — `validateMagicReturnTo`). Email body (Resend sender): one-tap button + plaintext link + the raw code as fallback + "expires in 15 minutes and works once". Delivery semantics (#3529): a provider *recipient refusal* (4xx except 401/408/429) is absorbed and the request still answers `sent` indistinguishably (`attemptAuthMailDelivery`); any transient failure rethrows → retryable 500, never a fake `sent`.

**Client (`src/auth-signin-ui.js`, strings in `strings/en.js`; host wiring `src/signin-entry.js`, restore in `src/account-client.js:122` `restore()` → `GET /api/account-session`).**

- One merged email form (#3341): there is no separate magic view; `showMagic()`/`showView("magic-request")` coerce to `password-login`.
- **The 401 gate (the heart of this pack):** module flag `passwordRecovery` starts `false`. It is set `true` **only** when `POST /api/auth/password/login` fails with status 401 **and** code `invalid_credentials` **and** the reply still belongs to the current session generation (`accountClient.owns`). Only then, and only if `signin-options` says mail is configured, does the panel render `signin.copy.035` ("Email me a sign-in link", `name="method" value="email"`), drop `required` from the password field, and appear as `signin.magic.action` / `signin.magic.instead` inside the Forgot-password and reset-request views too. Typing a *different* email clears the flag and removes the offers (`onInput`); submitting a different email clears it; `ui.clear()` clears it. A blank password on the *initial* form never sends mail (pinned test: "blank initial password never silently sends email"). After earning: clicking the email method, or submitting the earned form with a blank password (or the email submitter even with a filled password, which is then ignored), calls `requestEmailLink` → magic/request → `magic-sent` view (`signin.copy.012`: "Check {email} for your sign-in link", manual-code toggle `data-magic-manual-code`, "Use a different email" restart).
- **Link landing:** `consumeMagicLinkFromUrl()` + `classifyAuthLink(params)` run at mount. All auth params (`magic`, `reset`, `email`, and `signin`/`verify` on notice/invalid) are stripped via `history.replaceState` **before** redemption, so the proof cannot leak via referrer/history. `?magic=` → auto-redeem via magic/consume → `finish(view)` → `onSignedIn` (host restores the account session and any room/invitation context). `?reset=` → does **not** redeem; it opens the reset form holding `resetCode` in memory only. Malformed/competing proofs (`hasReset === hasMagic`, duplicated params, missing email) → `invalid` → `onMagicLinkFailure` + "This sign-in link is incomplete or invalid. Request a new link." Signup notices (`?signin=1`, `?verify=email`) classify as `notice` and redeem nothing.
- **Account-switch fence:** consume answering 409 `magic_account_mismatch` stores `pendingLink` and shows the switch panel (`signin.copy.006`); switching logs the current account out, calls `onSignInUncertain` (host re-restores/fences private room state), then redeems the **same unburned code**. Reset has the mirror fence via `reset_account_mismatch`.

**Adjacent, explicitly out of scope:** offline recovery *codes* (`/api/auth/recovery-codes/*`, legacy chain in `server/http.mjs:2631+`, slice 6) — a different credential, do not touch; email-verify and signup-notice mail (same mailer, purposes `email-verify`/`signup-notice`) — regression-cover only, do not redesign.

**The gating's user cost is real and unmitigated in copy (source-verified at `aaa749065a`).** A user who only ever used magic links, or has forgotten their password entirely, sees a password form with no email-link offer and no explanation. To earn the offer they must submit *some* password for that exact email and receive the uniform 401 — the panel never says this. The matrix is deliberately narrow (pinned in `tests/auth-signin-ui.test.js:445-455`): 401/`invalid_credentials` earns; 429 `rate_limited`, 503, a network error with no status, and 401/`account_session_required` do **not**; an obsolete-generation 401 does not; an emailed-link entry/reload does not. Editing the email after earning silently revokes the offer. None of this is explained anywhere in `strings/en.js`.

**Reset is a dead end for magic-only accounts (fresh code read, this lane, at `aaa749065a`).** `passwordResetAccount()` (`server/account-login-methods.mjs`) selects only `type='password'` login methods, and `resetPassword()` can only match a proof digest bound to such an account. But reset/request answers `sent` uniformly and *does* issue and mail a reset proof for an address whose only method is magic. The recipient clicks, gets the reset form, chooses a password — and consume must fail 401 `invalid_password_reset`, every time. The non-enumeration response shape is correct and must not change; the *mailed purpose* is wrong for this account class. (For an address with no account at all the mailed reset proof is a harmless dummy — that case must stay exactly as-is.)

**UNVERIFIED (labelled, do not assert):** real-inbox delivery latency, spam placement, and Resend domain authentication in production; whether mail-scanner/prefetch behaviour in common clients can burn a single-use link before the human clicks (consume is a POST driven by app JS after page load, so a plain GET prefetch cannot burn it — but a JS-executing scanner is untested); cross-device redemption (link requested on desktop, opened on a phone with a fresh slot) — supported by the slot-boot design and by the fresh-context browser check, never executed against production.

## 3. What fantastic means

End state, user-visible, measured against exemplars Slack's email sign-in link and Linear's emailed login link (one button in the email, lands signed in, code printed as fallback — match that shape, which the Resend template already follows):

1. **Earned recovery is discoverable in one read.** On the login panel, a user who cannot sign in can see — before submitting anything — that an emailed link exists as the recovery path and what unlocks it (one line, ≤ 20 words, e.g. naming that a failed sign-in or Forgot password offers "Email me a sign-in link"). Zero change to *when* the offer activates.
2. **The happy path is short and counted.** From earned offer: 1 click → `sent`; email in inbox **≤ 60 s at p95** in the production E2E (§4 step 4); 1 click in the email → signed in, **0 typing**, auth params gone from the URL, correct room/invitation context restored. Manual fallback: the 32-char code from the same email pastes into the sent view and signs in. Total from earned offer to signed-in: **≤ 3 user actions**.
3. **Every failure is legible and recoverable in place.** Expired/replayed/burnt link → visible "not valid / expired — request a new link" with a working request path, never a silent signed-out landing. Sent view states the two facts users currently cannot know: **"expires in 15 minutes"** and **"only the newest link works"** (requesting again kills earlier links, by design QAX-001).
4. **No dead-end mail, ever.** 100% of reset requests for an address held by a magic-only account produce an email whose link actually signs that user in (§4 step 2); 0% change to the response shape seen by any requester (non-enumeration preserved byte-for-byte).
5. **Production is proven, not presumed.** A repeatable, operator-owned E2E (§4 step 4) demonstrates request → real inbox → click → signed-in session on the production build, with timings recorded, and is re-run after every deploy that touches this piece. The UT row can then be re-graded from DEGRADED on executed evidence instead of a 405.
6. **Security invariants hold exactly as today:** codes hashed at rest, single-use, 15-min TTL, 5-attempt burn, newest-only, slot-before-burn, mismatch-before-burn, uniform responses for known/unknown/refused addresses, transient mail failure never fakes `sent`, no code ever in an API response or a log.
