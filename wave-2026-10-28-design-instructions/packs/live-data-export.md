## 1. The piece

**What it is.** The second half of issue #3585 ("R2 backup target breaks at current size: writer buffers the whole export in DO memory, and no restore path can read an R2 backup"). The nightly `room-backup` job exports the whole room store as NDJSON and writes it to a backup target. Today the only working target is Workers KV, which streams the export in ≤16 MiB parts and writes a manifest last. The R2 target (`ROOM_BACKUPS`) is the documented next target, but (a) its writer buffers the entire export in Durable Object memory before a single `put`, and (b) no restore path can read an R2 backup back. Bound PR #3622 ships only the interim guard for this (docs + no-silent-harm). This pack instructs the remainder: a streaming R2 writer and an R2 reader in both restore paths.

**Settled shape (Jill's decision, not the implementer's).** The remainder is built as the **KV-style part-objects variant (~12–18 lh)**, not the literal multipart-upload API prescribed in the issue text. R2 receives part *objects* plus a manifest object, in exactly the KV layout, so one manifest shape and one part-verification loop serve both transports. Evidence file §3 (cited in §2) prices the multipart variant at ~16–24 lh and states the part-objects variant "needs Jill's explicit acceptance as an equivalent" — Jill has given it; the task that commissioned this pack records it. The PR body must state this substitution explicitly (see §4 Step 1).

## 3. What fantastic means

The day this lands, binding R2 stops being a trap and becomes the documented, working second backup target:

- **Memory-bounded writer.** Writing a backup to R2 never holds more than **one ≤16 MiB part** (plus the streaming trackers) in Durable Object memory — the same bound the KV writer already meets — regardless of export size. Proven on a fixture of **at least 110,191,252 bytes** (the 2026-10-16 production-shaped size in `docs/BACKUP-DR.md`), i.e. a backup that leaves the current buffered writer within ~18 MB of the 128 MB DO limit completes, part by part, and verifies.
- **Manifest-last commit, identical shape.** An R2 backup is a set of part objects at `backupPartKey(key, i)` (`<key>.part-0000`, …) plus **one manifest object at the day's key itself**, byte-shaped exactly like the KV manifest (`kind`, `version`, `key`, `createdAt`, `bytes`, whole `sha256`, `parts[]` with per-part `bytes` + `sha256`). The manifest is written **last**: a day with no manifest has no backup. A torn export (count tear or trailer-hash tear) writes **no manifest**, throws, and leaves the day retryable — orphaned parts are unreferenced, never mistaken for a backup.
- **Both restore doors read R2.** `POST /api/operator/restore-from-backup` restores an R2 backup into an empty store with the identical fail-closed posture as KV today (404 unconfigured token / missing backup, 401 bad token, 409 non-empty store, 422 malformed or unverifiable, per-part and whole sha256 verified one part at a time through the existing replay session), and its result names the source (`source: "r2-backup"` vs `"kv-backup"`). `scripts/restore-room-backup.mjs --r2 <YYYY-MM-DD>` reassembles and replays the same backup locally through the same manifest validation.
- **One definition of "verified".** The writer's same-day skip check, `verifiedRecentBackup` (the store-relief gate), and both restore paths all accept exactly the same R2 backups: a current-version manifest whose parts sum and hash to the manifest. No surface reports a backup "verified" that no restore path can read.
- **The flag flips in the same change.** `R2_BACKUP_RESTORABLE` becomes `true` in this PR and only this PR (per the flag's own comment at #3622's head), the guard's fallback/refusal retires with it, and the docs flip from "Do not bind R2 as a standalone step" to the working bind-and-restore procedure in the same diff.
- **Exemplar to match:** the KV path in the same file. `writeKvBackup`'s streaming loop, manifest-last commit, and the endpoint's verify-each-part-then-feed loop are the proven in-repo patterns (KV proven at 90,688,789 B live and 110,191,252 B fixture). Fantastic here means "R2 is indistinguishable from KV in discipline", not a new design.
