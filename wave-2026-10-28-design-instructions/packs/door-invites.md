## 3. What fantastic means

The word "invite" becomes literally true: one place manages everything outstanding, and every state change takes effect immediately and visibly.

- **One Manage-invites surface per room.** Every outstanding share link, agent code (by `inviteId`), and guest invite appears in one list showing kind, grant/profile, created-by, status (`active`/`redeemed`/`revoked`/`expired`), expiry as a countdown, and joins remaining where applicable. Revoke/cancel is ≤2 clicks from the room screen, needs no request body knowledge, and the row flips to `revoked`/`cancelled` in the same view. Zero owners should ever be told to revoke anything "from the database": an ambiguous handle resolves in-product (candidates distinguished by created-at, profile, display name) in 100% of cases.
- **Minting exposes the server's real ranges.** Agent-invite UI offers the same TTL choice the API enforces (presets 1 h / 24 h / 7 d / 30 d, default 24 h); share-link UI already matches its range and stays the pattern. Mint → link/code in hand with a working Copy button in ≤3 clicks from the room screen, code shown exactly once, with profile and expiry stated in the share text itself (the current "Open this invite link" copy discipline in `src/agent-invite-ui.js` is the floor, not the ceiling).
- **Redemption is boring.** For a valid, unexpired invite, the acceptance harness (§5) passes 100%: preview discloses room title + grant + expiry + places left and nothing else; redeem succeeds once; a lost-response retry with the same `requestId` replays the same membership (already built — keep it). Dead invites answer in ≤1 s with the per-kind vocabulary of §1: an invitee can always tell *expired* from *revoked* from *used* for agent codes, and always gets "ask for a fresh invite" plus a request-access path for folded 410s.
- **Revocation is immediate.** After a revoke/cancel, the very next preview/redeem/join attempt (probe within 1 s) returns 410 `invite_revoked` / `link_unavailable` / `invite_unavailable` as applicable — no cache window, no "wait for expiry."
- **Room state and invite state never disagree in public.** Within 60 s of a room being archived, its `/r/` face shows an archived notice with no live join href, and invite preview for that room names `room_archived` at preview time instead of inviting a join that can only fail at write time.
- **`/join` never silently loses text.** A refresh at any point restores the filled request-access/entry forms from a same-browser draft (or warns before losing them); a nonexistent room id gets an honest not-found, in the same visual language as the (already good) bogus-code error: "Invite not found — this invite link is invalid, already used, or expired. Ask the inviter for a fresh link."
- **The pilot door stays a door.** The unauthenticated inventory in `docs/INVITE-ONLY-CHECKLIST.md` grows only by the named routes in §4, each with its checklist row in the same PR; `tests/invite-only-boundary.test.js` stays green. Exemplars to match: Discord's invite list (per-invite uses/max-age/expiry columns with per-row revoke), Slack's invite-link settings (one visible link, expiry, reset), GitHub's pending-invitations list (who, when, revoke). All three treat "what is outstanding and how do I kill it" as a first-class list — that list is what this piece lacks.
