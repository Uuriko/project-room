## 1. The piece

The **escrow keeper** is not a person, a member, or a UI persona. It is the mechanical settlement actor inside the bounty escrow: the code that pays, refunds, expires, and defaults bounties when time — not a human decision — is what is left. Its operational surfaces are the triggers that invoke it, the scan that decides what it sees, the records its actions leave, and the health signal that says whether it is stuck. This pack covers only those surfaces. Fund/accept/dispute journeys are pack `money-escrow`; conservation auditing is pack `money-conservation-audit`; global job-health grading is pack `operator-health-jobs`. Do not redo any of them here.

**Who the keeper is (verified at main `aaa749065a`):**

| Fact | Source |
|---|---|
| Rule actor | `server/bounty-escrow.mjs:110` — `RULE_ACTOR = { kind: "rule", id: "escrow-keeper" }`; every mechanical transition is attributed to it; a caller who triggers it manually is recorded separately as `triggeredBy` (null for the automatic pass) |
| Not impersonable | `tests/bounty-identity.test.js:236–242`: a participant submitting a transition with actor `{kind:"rule", id:"escrow-keeper"}` is refused `not_authorized` |
| Receipt issuer role | `server/bounty-escrow.mjs:1137`, `server/bounty-receipts.mjs:425`: receipts are issued with `issuer.role = "escrow-keeper"` — but see §2.5: in production those receipts are unsigned today |

**What the keeper does — the complete action set (`_keeperPass`, `server/bounty-escrow.mjs:2880`, plus the sweep):**

| Bounty state + condition | Keeper action | Money / record |
|---|---|---|
| `proposed`, deadline passed, any snooze lapsed | `expired-unfunded` (`_expireUnfunded`) | No money moves; state → `cancelled`, label "Expired", event `bounty.declined` with `automatic: true` |
| `accepted`, `challengeEndsMs` passed | `approved` (`_approve`) | Journal move attributed → approved, memo "challenge window passed unchallenged"; state → `approved`. **Not yet paid** — see the two-step rule below |
| `approved` (always actionable) | sweep (`_sweep`, via `closeEpoch` only) | Worker payable = amount − `floor(amount × 1/100)` fee; fee → pool payable; claim bond returned; settlement kind `verified-complete`; state → `paid`; receipt type `payout-released` with gross/fee/net millis |
| `submitted`, deadline passed | `refunded` (`_settleUnverified`, free-miss) | Escrow locked → poster payable in full; worker settles at 0; settlement kind `unverified` |
| `funded` / `claimed`, deadline passed | `refunded` (`_timeoutRefund`) | Locked → poster payable in full, no fee, memo "timeout: award refunded in full, no fee"; a no-submission claimant records a flake strike and the claim bond forfeits to the pool (returned if the work had been submitted and refunded through no fault of the claimant) |
| `disputed`, dispute already terminal (`resolved`/`withdrawn`) but bounty unsettled | retry `_settleDispute` → `released` or `refunded` | The inline finalize handler must have thrown; the keeper retries immediately, not at the timeout |
| `disputed`, open, opened > 14 days (`DISPUTE_TIMEOUT_MS`) | `released` (timeout default RELEASE) | `_settleDispute` with outcome `timeout-default`; a pre-#3727 legacy row with no seated decider returns the dispute bond to the challenger instead of compensating the worker |

**Two-step rule (by construction, never collapse it):** `closeEpoch` snapshots its rows up front, so a bounty approved by a pass is **not** swept by the same pass. Approval is one tick, payment is a later tick — exactly as the old manual double invocation behaved (`server/bounty-epoch-keeper.mjs` header, :3–20). Note also that `finalizeBounty` runs only `_keeperPass` — it does **not** sweep an `approved` bounty; the sweep exists only in the `closeEpoch` loop.

**The three triggers (what invokes the keeper):**

| Trigger | Surface | Verified facts |
|---|---|---|
| Automatic job `escrow-epochs` | `server/jobs.mjs` (job definition, cadence `MINUTE_MS`); `server/bounty-epoch-keeper.mjs` (`progressEscrowEpochs`) | Cadence 1 minute, runtimes worker + node. `enabled` only when `escrowEpochNextDueAt(store, now) != null`; `disabledReason` = "No bounty is waiting on an epoch close". Runs `progressEscrowEpochs`: one `closeEpoch` per room with due work, per-room throws isolated (one room counts `failed += 1`, others continue) |
| Manual per-bounty `finalizeBounty` | HTTP `POST /api/rooms/{roomId}/bounties/{bountyId}/finalize` (`server/bounty-escrow-routes.mjs`, `escrowRoute === "finalize"`; dispatched in `server/http.mjs`); MCP `bounty_finalize` (`server/mcp-full-profile.mjs:517`) | Permissionless and purely mechanical — any authenticated room member / lane caller may trigger it; the keeper, not the caller, is the actor. Runs exactly one `_keeperPass` on that bounty; refuses `invalid_state` "bounty is ${state}: nothing to finalize" when nothing is due |
| Manual per-room `closeEpoch` | HTTP `POST /api/rooms/{roomId}/credits/epoch/close` (`docs/openapi.yaml` summary "Close the credit epoch (manual keeper)"; route `escrowRoute === "epoch-close"` in `server/bounty-escrow-routes.mjs`) | Same pass over the whole room. **Deliberately not an MCP tool** (`docs/BOUNTY-MCP-TOOLS.md`, "Deliberately not exposed": `decideDispute`, `closeEpoch`, and `resolveSybilFlag` "remain outside the agent surface because they require human or operator standing") — the automatic job and this HTTP route are the only whole-room doors |

**What the keeper sees:** the due-scan in `server/bounty-epoch-keeper.mjs` (`DUE_WHERE` over `bounty_records`, actionable states `proposed/funded/claimed/submitted/accepted/disputed/approved`), which mirrors `_keeperPass` condition for condition, plus `escrowEpochNextDueAt` computing the next millisecond any bounty becomes actionable. Inside a pass, `closeEpoch` (`server/bounty-escrow.mjs`, keeper/epoch section) snapshots **all** rows in the actionable states (including `submitted` — the omission of that state from an earlier snapshot was the live guardian-census F1 stall, recorded in the comment in `closeEpoch`), runs each bounty's action in an isolated nested transaction (a throw rolls back only that bounty, #3275), and emits one `epoch.closed` event carrying the summary (`approved / swept / refunded / released / paid / expiredUnfunded`, plus `failed: [{bountyId, code, message}]` when present) and `triggeredBy`.

**What the keeper leaves behind (its only outputs today):** the `epoch.closed` room event; a `finalize` receipt for the manual per-bounty door (`{ kind: "finalize", bountyId, action, at, actor: RULE_ACTOR, triggeredBy, signed }`); settlement records and journal moves attributed to the rule actor; a numbers-only job summary `{rooms, due, approved, paid, refunded, released, expired, failed, errors, overdue}` from `progressEscrowEpochs` (the heartbeat keeps only numbers/booleans), and a `console.info` line `room.escrow_epochs` emitted only when `rooms > 0`. `overdue` in that summary excludes `approved` rows by design — an approved bounty is mid-progression, not stuck. There is **no client or operator UI for any of this**: `operator.html` has Status / Find leftovers / Purge plan / Recent operator actions and no escrow section (verified at this SHA), and the only human-facing mention of the keeper in the web surfaces is prose in `offers.html` ("the settlement keeper pays it in a later epoch sweep").

**Drill evidence — the keeper working unaided (executed, on file):** MEMORY.md, "FS-FUND leg-8 settlement check: PASS (verdict of record, read 2026-10-24T02:35Z)": both First Shift drill bounties were **paid by the escrow keeper unaided** — FS-01 settled 2026-10-24T02:26:49Z (worker 1.98 / pool fee 0.02 on a 2 cr award) and FS-02 settled 02:27:48Z (worker 3.96 / pool fee 0.04 on a 4 cr award); closing balances builder payable **105.94** / locked 0 / attributed 0, sponsor total **94** (23 payable / 71 locked), pool **0.06**, conservation **200.00 exact = genesis**. Qualifications carried from the same record set: leg-8 rests on a single operator read; production receipts are **unsigned** (money-core deep-dive, 2026-10-25: Invariant 17 DOES-NOT-HOLD in production — machinery holds, no signer is wired, keeper movements issue no signed receipts); and UT wave 2's rollup (`~/workspace/wave-2026-10-27-user-testing-2/pods/ROLLUP.md`) records that the keeper-sweep 1% fee has **never been executed end-to-end by a user-testing lane** — the drill proved the keeper's mechanics and conservation in an operator-run cohort, not signing, discoverability, public readability, or a stranger executing the fee journey.

## 2. Current state

1. **No keeper preview exists — nobody can see what the keeper will do, or when (read at source).** No read surface exposes, for any bounty or room: whether it is due, which `_keeperPass` condition it is waiting on, the millisecond it becomes due (`escrowEpochNextDueAt` is computed only inside the job's `enabled`/`nextDueAt` gates in `server/jobs.mjs`), or which action will fire. `listBounties`, balances (`GET …/credits/balances/{identity}`), and history (`GET …/credits/history/{identity}`) return state and money, never the keeper's next action or due-at. The only way to answer "when will I be paid / why hasn't this refunded?" today is to read `DUE_WHERE` and `_keeperPass` in source. The manual door is no better: pre-due `finalizeBounty` refuses with the bare "nothing to finalize" and no due date.
2. **Automatic-pass failures are invisible in detail (read at source).** When the automatic job runs, `closeEpoch`'s per-bounty `failed: [{bountyId, code, message}]` detail exists only inside the `epoch.closed` event payload. `progressEscrowEpochs` collapses it to a count (`failed`/`errors`), and the job heartbeat keeps numbers only — so health can say "3 failed / overdue 2" but no surface anywhere names **which** bounties, in **which rooms**, **why** each failed, or **how long** each has been due. Whole-room throws are worse: the reason goes only to a truncated (200-char, one-line) `console.error` line in `progressEscrowEpochs`. A poisoned bounty is therefore a number, not a work item.
3. **The stuck-state defect class is real and already bit once (executed evidence, in-code record).** The comment in `closeEpoch` records guardian census F1 (2026-10-18): submitted bounties past deadline counted due + overdue every tick while no keeper action could ever touch them, `failed` stayed 0, and nothing threw — the rows were simply never read by the snapshot. That instance is cured, but the detection gap that hid it is not: today's only stall signal is the aggregate overdue count going non-zero in the numbers-only summary, which fires without naming a single stuck row, its room, or its cause.
4. **There is no keeper pause (read at source).** No global or per-room keeper kill flag exists at this SHA — no flag is checked in `progressEscrowEpochs`, in the `escrow-epochs` job definition, or in `closeEpoch`/`finalizeBounty`. If the keeper itself misbehaves, an operator has no keeper-specific brake: the choices are "let it run every minute" or intervention at the whole-deployment level. Manual and automatic triggers are also indistinguishable as a control problem — there is no way to stop the machine while leaving deliberate human-triggered settlement available as a considered escape hatch, because no such distinction is implemented.
5. **Keeper settlements are unprovable from inside the product (executed + read).** (a) Receipts are unsigned in production — Invariant 17 does not hold, no signer is provisioned, `BountyEscrow` is constructed with `receipts = null` on the production path and `_issueReceipt` returns null when no signer is configured (`server/bounty-escrow.mjs`, `_issueReceipt`: "Returns null when no signer is configured (production key provisioning is a later slice)"); a keeper payout therefore cannot be shown as signed, and no step below may claim otherwise. (b) The FS-01/FS-02 drill evidence (§1) lives in external files (MEMORY.md and programme records), not in any product surface: from a bounty's own history you can see rule-actor moves, but nothing labels a settlement "automatic, unaided" vs "manually triggered" except the `triggeredBy` field in the `epoch.closed` event / finalize receipt — the list, balances, and history reads do not project it. (c) There is no repeatable in-repo drill: no test replays the FS-01/FS-02 shape (two awards, keeper-only settlement, exact 1.98/0.02 and 3.96/0.04 splits, conservation 200.00) as a regression.
6. **The two-step close reads as a stall (by construction).** An `accepted` bounty approved on tick *t* is paid on a later tick; `overdue` deliberately excludes `approved`, so health stays green while the worker is unpaid, and no surface says "approved — sweep pending, expected next tick". At the 1-minute cadence the gap is normally ≤ ~1 minute, but if the job is gated off or a runtime is down, the gap is unbounded and indistinguishable from health. UNVERIFIED: no executed probe at this SHA measures the real approve→pay gap in production; §5 makes the implementer measure it in the harness, not assert it.
7. **Ledger reads are scoped away from any overseer (read at source).** Balances and history are readable only by the lane itself or the room owner (`canReadLaneLedger` in `server/bounty-escrow-routes.mjs`, #3281 — a deliberate privacy rule, not a bug), and the MCP tools read only the caller's own lane (`docs/BOUNTY-MCP-TOOLS.md`). An operator who is not the room owner therefore has **no** sanctioned read of a room's keeper queue at all — which is precisely why §4's status read is owner-gated, not operator-wide.
8. **What is NOT broken (do not "fix" it):** the keeper's mechanics. Per-bounty atomicity (#3275 isolated rollback: a failed bounty applies nothing and does not wedge the epoch), the two-step semantics, dispute-terminal retry, the free-miss and timeout paths, and the FS drill's exact conservation all stand on executed evidence. This pack adds **visibility and one brake**; it changes no keeper decision, amount, window, or ordering.

## 3. What fantastic means

A room owner, a worker, or an operator can answer four questions from product surfaces alone, in one read each, without opening source:

- **"What happens next to this bounty, and when?"** — every bounty read carries its keeper preview: not-due with the exact condition and ISO due-at, or due with the named action (`approved`, sweep/`paid`, `refunded`, `released`, `expired-unfunded`) the next pass will take.
- **"Did the machine do that, or did a person trigger it?"** — every keeper settlement is labelled on the list/history read as automatic (`triggeredBy: null`) or manually triggered (with the triggering lane), matching the `epoch.closed` event exactly.
- **"Is anything stuck, exactly what, and why?"** — an owner-gated keeper-status read names 100% of due-and-unactioned bounties for the room (id, state, due-since, age, last failure code + message), and the count on that read always equals the job summary's `due`/`overdue` arithmetic for the same instant.
- **"Stop the machine, only the machine."** — one operator-set flag halts automatic keeper passes within one tick (≤60 s), shows as a named disabled reason on job health, and leaves manual `finalize`/`epoch-close` working as the deliberate escape hatch.

Numbers that prove it: preview-vs-pass agreement **100%** over a state × condition matrix (every actionable state, every `DUE_WHERE` branch, plus the not-due cases) — the preview is generated from the same predicate family the pass executes, and a test asserts preview action == actual `_keeperPass`/`closeEpoch` action on identical fixtures; census completeness **100%** (a fixture with *k* poisoned bounties yields *k* named census rows, zero unnamed counts); the FS drill replayed as a test settles both awards keeper-only with the exact historical splits (1.98/0.02, 3.96/0.04) and conservation **200.00 exact**; zero money-semantics drift — every pre-existing keeper/escrow suite passes unmodified except where a suite pins a response shape this pack explicitly extends. Exemplar worth matching for the status read's shape: the job summary's own discipline in `server/bounty-epoch-keeper.mjs` (numbers verbatim, failures named with code + message, absence rendered as a reason — never as an error).
