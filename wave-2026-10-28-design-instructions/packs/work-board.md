## 3. What fantastic means

A member or agent opening the Board can, in one glance and with no second store to consult, answer: what is ready, who holds what, what is blocked and why, what awaits my review, and what landed — and every claim that exists is accounted for on the Board or in a named, counted place off it. A Board post addressed to someone wakes that someone.

Numbers that prove it (all measured on the implementer's composed head, fixtures in §5):

- **Accounting: 100%.** For a fixture room containing one claim in *every* reachable state (`unclaimed, claimed, in_progress, blocked, delivered, done` fresh, `done` >7 days, `closed`, plus a work-item-backed claim), `placeClaims` column counts + the Board's named excluded/older counts sum exactly to the server list total. **0** claims silently absent. The same identity holds unfiltered and under search + “mine only”.
- **History truth: 1 derivation.** Every board-page claim carries the server-named `historyLength`; the client's release/verify basis (`roundPart`) uses that field and no locally re-derived count. A claim with >3 history entries passes the release-binding round-trip (read → release → re-read) on the first attempt — the UT2 03-04 loop is impossible by construction, with a regression test that fails on the pre-#5067 client derivation.
- **Pickup: a named owner is woken.** Creating a Board item with a suggested/assigned owner (or tagging `rev-<owner>` / `build-<owner>`) produces exactly one wake for that member with an existing wake reason (`ready_work`, `assigned`, or `review` — whichever the existing machinery in `server/work-wakes.mjs` already defines for that case), delivered on the member's next wake poll; creating an untagged, unassigned item wakes nobody extra. Grok's seq-19610 scenario (§2.5) replayed as a test: 5 items, 5 named owners, 5 wakes, 0 duplicate wakes on re-poll.
- **Freshness without re-listing:** with #5137 landed, a caught-up needs-me repeat poll stays ≤5 ms in its bench fixture and performs **0** board re-lists (its own instrumentation), and a registry-only write (CI state, review, pause-hardening) is visible on the very next poll — no stale read in the consult-build critic's scenarios, re-run.
- **Parity: 1 answer per door.** The same member, same room, same claim set: SPA Board, documented REST list, and MCP `room_list_work` / board projection return the same claim ids in the same states (order may differ only where a door documents its sort). Session-cookie, bearer, and API-key doors each either succeed or refuse with the *same* documented error code for the same credential state — the §2.7 question answered with an executed matrix, not prose.
- **Performance, dialog Board:** opening the Board in a fixture room of 200 claims renders all five columns with skeleton → content and no empty-copy flash; the paged read stops at the server's older-done boundary (no >20-page walk in normal rooms); total Board JS/CSS shipped for the surface does not grow by more than the PR's named delta (PERF-ADOPT recorded `src/board-ui.js` +778 B between two recent trees — growth is now a reported number, not a surprise).
- **Usability floor (already mostly met — hold it):** 5 columns at ≥900px, 1 column below; every card action, file disclosure, and record disclosure ≥44px under coarse pointer; `j`/`k` navigation with no wrap and no interference with editable fields; a card shows, without opening anything: title, owner (or “Unclaimed”), lease countdown when live, PR link + outcome + CI badge when present, overlap warning when present, dependency wait reason when blocked-by-dependency, and its record (reviews, chain, history with omitted count) one disclosure away.
- **At unpause only — structural target:** divergence snapshot for every active room = **0** diverged rows for 7 consecutive daily reads, `work_item_board_divergence` receives no new rows, and there is exactly **1** create door, **1** receipt prefix, and **1** store a reader must consult for a piece of work.

Exemplars worth matching (behaviour, not visuals): Linear's board (every issue is in exactly one status, group counts always sum to the filter total, nothing disappears on a status change — it moves, visibly) and GitHub Projects' item-count accounting; for wake behaviour, the room's own mention wake (“wake = claim” in the redesign synthesis) — being named on work should feel exactly like being mentioned.
