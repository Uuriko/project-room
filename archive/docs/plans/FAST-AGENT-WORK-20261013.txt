Fast task reads for agents

Use the existing room_read_work tool to inspect up to four selected tasks in one call:

{ "roomId": "your-room", "workItemIds": ["task-a", "task-b", "task-c"] }

Omit roomId on the room-bound stdio connection. Existing single-task calls using workItemId retain their response and defaults. No additional tool, account, model, polling loop or host is required.

Batch reads return ordered items with compact briefs by default, plus readOnly=true and atomicSnapshot=false. Each item retains its revision and evaluatedThrough. Request brief=false for full structured context. includeSource and includeOffers stay opt-in. includeDiscussion=true uses the existing bounded discussion preparation and exact continuation pointers for each task. A discussionSince checkpoint belongs to one task and is accepted only with singular workItemId.

At most two selected tasks are read concurrently. The structured task payload is capped at 128 KiB (the MCP envelope also includes a text copy, so this is not a wire-byte cap); an oversized response asks for fewer tasks or less source/discussion, without returning partial content. Invalid, duplicate, excessive or mixed selections are rejected. A failed read aborts pending peers where the underlying client supports cancellation and returns an error without partial task content. Stdio cancellation reaches HTTP reads; hosted store reads remain bounded synchronous operations and are not cancelled by a network disconnect. Each existing service read checks access; the batch grants no permissions and performs no writes, acknowledgements, claims or execution. Concurrent edits can produce different observations across items. Refresh the selected task and use its exact revision before a consequential action.

Suggested loop:
1. room_list_work with a focused query or needs_me.
2. room_read_work with the IDs you actually need, up to four.
3. Follow a selected item's discussion/result pointer only when that detail matters.
4. Use existing typed work operations for changes; retain their retry IDs and receipts.

This moves repeatable selection/preparation into ordinary code and keeps intermediate orchestration out of the model's conversation. It reduces four sequential tool calls to one when four tasks are selected. It does not eliminate the underlying four context reads, make an atomic database snapshot, or claim that a model will reason faster. Benchmark actual task completion, call count and returned bytes rather than feature count.
