# Exact posting origin for adopted channel copies

Source `c6fe84ca1ba1557cdaf2fb3b4540c646d75b78f0`, isolated GitHub main base `00888c52110d36250d3e07629036701b72926d09`. Local synthetic tests only; no production calls, deployment, or confirmation of the live 500 cause.

A legal public thread reply with `alsoSendToChannel:true` creates `<replyId>:channel` in the SAME event. Legacy initialize/import can leave messages table rows absent until backfill. Adoption previously looked only for a message.posted whose literal posted ID equaled each current message ID. The derived copy has no independent posting event. It therefore threw plain `Error: Missing original message posting sequence`, rolled back and surfaced as HTTP 500. A three-message/four-event disposable fixture reproduces it without scale or private data. The exact original failure stack is retained.

The production change is confined to messages-store.mjs. It keeps exact posted-ID lookup first. If absent, one trailing `:channel` can address the parent's existing expression-index entry. A shared posting/copy predicate now serves this origin check and the preexisting archive spot-check: real message.posted, also-send enabled, actual reply, no DM or work context, exact deterministic copy ID. It verifies copy author/time, reducer-default channel, null reply/DM/work fields, and unedited body equality. Independently edited/deleted current copy content still comes from the validated current state. The canonical copy receives the exact parent posting sequence, not a guessed/current sequence. No new index, DDL, fallback ID scan, grants, schema, or metadata/hash bypass is added. SQL remains an indexed message-ID range; this is not a claimed constant bound over arbitrarily many events for one ID.
