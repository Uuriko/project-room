# ACK proposal only — not implemented

Read-only source at main dd9: terminal chat receipt ACK call is after durable posted/discarded state. Bridge.ack is also used for unsupported wakes, permission decisions and claim cleanup, so blanket batching there would expand semantics. The REST ACK route has no explicit signal-count cap; its shared JSON limit is 16 KiB, and SQL is already chunked. Credential writes have burst 40 and refill one per second; ACK also has a 120-per-address-per-minute limit.

Snapshot 2026-11-03 23:27:10 UTC: 297 terminal primary local receipts; 290 singleton groups, four groups of two, three groups of three. Current-host log segment contained 47 chat rate-limit and 21 poll rate-limit diagnostics. Those diagnostics do not identify the bucket, endpoint or actual request count; they do not prove ACK dominates. Shared client cooldown is a validated monotonic barrier, not a token bucket: concurrent requests can resume together after a valid Retry-After.

Possible later experiment: coalesce only terminal chat-receipt ACKs, captured by same client/room/fencing token, with at most 50 unique IDs and exact serialized bytes below the existing 16 KiB. A short bounded window could collect four concurrent terminal singletons into one ACK. Every caller awaits actual batch completion; failures reject all affected callers, leave terminal receipts durable, and rely on existing normal replay (no autonomous retry or model/write reexecution). Abort rejects waiting callers; never ACK queued/started/result/formal-before-delivery. Exact retry remains idempotent.

Source-derived upper estimate at four concurrent singleton completions: four ACK requests to one (75% fewer ACK requests); if all also post answers, eight total writes to five (37.5%). These are unmeasured potential savings, not live results. Root explicitly held this work to prioritize fresh discovery. No ACK batching, proactive token bucket, quota increase or live modification was implemented.
