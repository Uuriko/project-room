# room-lifecycle-set — suspected bugs (WAVE-400)

Read-only archaeology; nothing fixed. Line numbers are for the current checkout (origin/main c5d1c313a).

## Suspected

- **`server/room-context.mjs:21-25` (canonical) — `createHash.update(undefined)` throw on malformed fields.** `canonical` calls `JSON.stringify(value)` for leaf values; if a pushed field is `undefined` (e.g. `item.decision.decision` at line 114, or `next.action`/`next.memberId` from `nextWorkStep` at lines 103-108, if a work item has a bare `decision: {}` object), `JSON.stringify(undefined)` returns `undefined`, and `hash.update(undefined)` throws a TypeError — turning a single malformed work item into a 500 on every context read for the whole room. Low likelihood (reducers normally populate these), high blast radius. Not verified against live data.
- **`server/room-guide.mjs:131-132` (step, choice close) — state advanced under a stale `store.room(roomId).state` read.** Line 128 re-reads `store.room(roomId).state` for `pickedChoice`, but `starter`/`choices` were read from the *earlier* `state` at line 108. Inside `step()` this is consistent (single transaction, no writes between), so benign today — but the two reads make future edits fragile: if a write lands between them, the close could proceed on a stale starter owner check. Readability/maintainability risk, not an active bug.
- **`server/room-guide.mjs:140` (choiceIdFromItem) — id parsing assumes no spaces in choice ids.** The done-stamp note is `choice:<id> <title>` and the id is recovered via `.split(" ")[0]`. Any choice id containing a space would be truncated and `registry.get` would miss, leaving the agent-assignment stage permanently stuck (returns `null` forever). Choice ids come from starter templates; none have spaces today, so this is a latent contract, not an active bug.
- **`server/room-lifecycle.mjs:118-124` (createAccountRoom idempotency check) — comparison uses trimmed `title`/`purpose`/`displayName` and raw `kind`, but `roomKind` normalization differs.** The check compares `roomKind(state.room) === kind` where `roomKind` defaults unknown/missing kinds to `"personal"`, while `kind` was validated against `ROOM_KINDS`. Consistent for stored rooms (kind is always written from the validated request), but if an old projection carries a non-standard kind, a legitimate identical retry would 409 `room_exists` instead of returning `duplicate: true`. Edge case only; not observed.
- **`server/room-guide.mjs:63` (installGuideCommandHook) — prototype patching applies to every RoomStore subclass instance process-wide.** The `__roomGuideHook` guard prevents double-install, but any code path that constructs a store for a room where the guide must NOT run (e.g. a replay/migration tool using the same class) still gets the hook, because the patch is on the prototype, not the instance. `runGuideStep` is inert without `starterSeeded`, so blast radius is limited to rooms with that flag set outside production.

## Checked and found clean

- `migrateRoomLifecycleV28` / `verifyRoomLifecycle` SQLite three-valued-logic: `IS NOT` on nullable operands is correct (NULL `IS NOT` NULL → false), so the backfill is idempotent and the audit has no NULL false-positives.
- `createAccountRoom` request validation: rejects non-objects/arrays, missing fields, and unknown fields (exact-field check incl. optional `intent`/`start`/`templateSlug`); 409 `room_exists` when the id belongs to a room the account isn't bound to (`bound` null ⇒ `same` falsy).
- Creation gate: zero memberships ⇒ first room OK; otherwise owner/`manage_members` in an active human membership, or spare growth credits with `foundedWithGrowth`; growth-funded rooms never unlock the 100-room allowance; provisional accounts blocked (403).
- `refuseArchivedWrite` placement covers commands, history import, and join paths (7 files import it); archive does not block reads/streams/export.
- `buildRoomContext` input validation (RangeError on bad room/viewer/sequence/cursor/clock); `context_version` excludes `evaluatedAt`, cursors, identity, and heartbeat time, so the `not_modified` protocol in `store.roomContext` is stable; all lists sorted before hashing.
- Guide step idempotency: welcome message id `gw-<roomId>` and assignment id `stableEventId("ga", roomId\0agentId)` make re-runs no-ops; hook and flush both swallow guide failures so the caller's command never fails because of the guide.
