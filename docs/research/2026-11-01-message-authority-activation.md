# Explicit message authority activation

The deployed canonical engine has no automatic production conversion. This change connects it to the existing token-protected operator surface:

- POST `/api/operator/messages/authority/plan`: `roomId`, `reason`, optional boolean `reverse`.
- POST `/api/operator/messages/authority/prepare`: `roomId`, `reason`, the returned `planHash`, and an explicit stable `requestId`. Forward replay only.
- POST `/api/operator/messages/authority/execute`: the same fields, the returned `planHash`, and an explicit stable `requestId`.

Keep the exact execution input and request ID on an unknown result. The original saved response is returned on an identical retry, including after later room writes; it is a receipt of the original change, not current room state. Changed input under that ID conflicts. Read the room again to establish current state.

Planning reads capped inventories and records an operator audit. It does not hydrate, replay or certify the room, and does not claim the room is qualified merely because inventory succeeded. Execution re-inventories in its transaction, compares the exact source/proof fingerprint, requires caught-up message backfill and exact-head parity, validates serving proofs, invokes the existing migration, and commits its saved response in the same append-only audit transaction. There is no new table, schema version, automatic global backfill, rolling-storage flag or agent permission.

The fingerprint binds direction, room/head/event data, projection bytes, all bounded message payload/proof fields, work/body rows, current metadata/content proof, replay/certification anchors, and replay snapshot/part bytes. A parked backfill or applicable recorded integrity failure refuses. A changed cursor can require a fresh plan even without a new room event; this is deliberate reconciliation.

## Explicit targeted preparation

An eligible inventory can still have a replay cursor behind the room head. In that case execution refuses `authority_not_ready`; it does not start global replay. The separate prepare phase advances only the selected room by at most 200 events using the existing reducer, cursor and snapshot engine. Planning remains inventory plus audit, and execution remains the conversion boundary.

Preparation first repeats the bounded inventory and plan hash check. In addition to the existing source caps, it admits at most 1,024 target snapshot-part rows, including detached anchor controls, with at most 1 MiB aggregate snapshot/part input. Numeric controls receive SQL storage-type/range checks and byte admission before materialization. Existing cursors must retain their exact event anchors; missing/torn snapshots, invalid cursors and any residual detached anchor refuse before replay can reset or repair them. A genuinely absent cursor may start from empty only against the admitted source and healthy independent current metadata proof. Archives, recorded blocks, corrupt body/entity proofs and missing current metadata proofs refuse.

Each resulting reducer state must fit the existing 1 MiB payload and 1,024-message limits before any checkpoint, quarantine stash or final publication. The admitted serialized state is reused for the checkpoint write. Final overlay output is admitted too. At a caught-up head, existing targeted exact-head parity must pass inside the same outer transaction before publication can commit. A valid JSON checkpoint alone cannot establish serving provenance: a staged-body tamper regression fails before this final check and then proves complete rollback. Any output, reducer/quarantine, final parity or saved-audit failure rolls back the entire prepare slice. No block is silently healed and no historical proof baseline is manufactured.

Independent review also reproduced two shared replay trust gaps: reordered posting events could overwrite an authoritative posting sequence and refresh its proof, and a missing referenced entity could be recreated from a changed log. Publication now validates current canonical proof/count, every referenced ID and its proof, archived membership counts, and all indexed fields through the existing complete row comparator with replay posting provenance, pins and thread ancestry. Existing authoritative rows and their proofs are preserved byte for byte; replay excludes them from initial deletion and upserts. This guard applies to shared backfill publication, while ordinary per-message writes retain their existing path. Prepare separately refuses missing referenced IDs before entering replay. Global and operator negatives cover both canonical and reference authority; legitimate reconstruction preserves equivalent JSON representations without normalizing or reproofing them.

The response's `preparation` records `events`, `replaySeq`, `appliedSeq` and `caughtUp`. Completion requires both the replay and applied cursors at the current head. For another step, obtain a fresh plan and use a new request ID. Preserve the exact prior input on an uncertain result: retry returns its original saved receipt even after later steps or writes, without consuming another replay slice. Prepare receipts use a separate idempotency namespace from execute receipts, preserving the existing execute prefix and API.

The focused prepare suite includes capped snapshot/part admission spies, malformed part controls, no-reset corruption cases, valid chunked continuation, output expansion, proof corruption, quarantine/audit rollback, another room remaining untouched, retries and the authenticated HTTP route. Its actual workerd fixture prepares 200 events, disposes/reopens the isolate, appends a legitimate message, prepares the remaining 103 events, restarts, retries the original receipt, converts with the existing execute API and restarts again. All 301 messages and the appended body survive; the unrelated room has no replay cursor. These are synthetic local checks, not a production conversion or Worker CPU SLA. Large or archived history still requires the separate bounded-format work.

That same persisted Worker fixture then reorders two source posting sequences, restarts between preparation slices, and proves final publication refuses while preserving original message sequence/proof bytes. After deleting one canonical row and changing its event body, another restart preserves the absence and preparation refuses instead of recreating a forged entity.

## Bounds and exclusions

Admission precedes hydration, parity, migration and payload fingerprinting. Indexed per-room inventories stop at cap plus one. Current conservative limits are 512 KiB of raw projection, head/event rows at most 2048, 1024 message rows, 128 work rows, 1024 body rows, and 1 MiB per domain. The conservative hydrated bound also must fit 1 MiB; repeated body references count repeatedly. Hash and cursor anchor strings have separate small caps. These are source-size limits, not a production CPU SLA; SQL sizing of a pre-existing oversized record is not claimed to be a constant-cost operation.

Archived rooms with a message archive prefix refuse. The existing parity implementation compares archived payloads by count and migration uses a reconstruction scope; this first operator path must not convert those unqualified histories. Oversized/archived rooms require the separate bounded continuation design. Do not enlarge caps, archive data or replay globally merely to force eligibility. In particular this initial path cannot remove muse-room's large history blob yet.

Reverse requires a fresh plan against current data and preserves intervening legitimate writes. A reproduced engine defect is fixed here: matching `body` and `record_json` could previously be converted back inline despite a mismatched independent message proof. The direct regression fails before the new reverse guard and passes afterward. The guard validates canonical serving proofs before removing authority. It does not manufacture a historical baseline, clear quarantine or use old projection bytes as a restore.

Parity's nested certificate invalidation is rolled back with a failed outer execution transaction. The operator always performs fresh verification on the next attempt and never treats the old certificate alone as sufficient. Failure after representation change but before saved audit publication rolls back both; a retry can then complete once.

## Qualification

Focused Node tests cover actual HTTP operator access, inventory-only planning, direction/source/intent conflicts, saved-response retry after later writes, audit-failure rollback, archive refusal, cap-plus-one in every normalized domain, UTF-8 payload sizes, same-head drift and reverse proof refusal. Existing engine tests cover post/edit/reply/delete, archived engine semantics, export/restore, missing rows and bounded selected edits.

A separate local workerd fixture is disposed and recreated with a persistent SQLite directory between stages. It converts, restarts, reads, edits, restarts, retries the original conversion, reverses current state, restarts and reads the edited result. Another real restart preserves corrupted canonical rows and proves a fresh reverse plan cannot authorize them. This is actual workerd restart evidence, unlike constructing another RoomStore within one running isolate.

The 1000-message workerd sample retains 1002 events, 257608 bytes of projection and 461780 message-row payload bytes. Conversion leaves 751 bytes of metadata with no messages array. One observed plan/execute pair took about 14/81 ms local wall time. These measurements do not establish production latency or Worker CPU/billing. A larger-body sample correctly exceeded the hydrated bound; its refusal is retained, and limits were not raised.

The prior release c1c92 remains live while this change is reviewed. No production room is converted by these tests, no public Dot plugin route is qualified, and the next real hourly integrity success remains a separate requirement.

## Independent admission review and cure

Read-only review of 9dc769a1 found an actual malformed-storage admission gap: non-STRICT SQLite permits oversized TEXT in INTEGER-affinity fields, and the fingerprint formerly selected fields omitted by byte counts. Eight failing controls now cover the room head, event/message sequences, work revision and proof/cursor sequences. The cure sizes all explicitly materialized fields, checks proof/cursor bytes before projection reads, bounds the room sequence through SQL without returning malformed values, and replaces SELECT * fingerprints with explicit fields. The independent reviewer repeated the 2 MiB work revision probe and confirmed refusal before payload materialization.

Cured qualification: 25 operator tests and four actual Worker checks pass; preflight passes. The near-cap sample remains eligible with the more conservative inventory: 1,002 events / 425,657 bytes, 1,000 message rows / 472,679 bytes, 257,608 projection bytes and 730,287 estimated hydrated bytes. Local workerd plan ~14ms / execute ~83ms is wall time, not a production CPU guarantee. No production room conversion is claimed.
