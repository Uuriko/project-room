Why a per-room cursor is insufficient
A single normalized room can contain unbounded message/proof/work/event history.
readCurrentRoomForAudit builds all maps and canonical messages, recomputes derived
privacy/summary/thread/history membership, and compares full counts. _replayRoom
loads all retained event rows then replayEvents, retaining an in-memory projection.
The text/charter/reply/help validators retain their own history/fact maps. Finishing
one room in one call preserves the current full-target bottleneck. Nor can the
existing singleton progress safely store an arbitrary reconstructed room object
under its1MiB metadata bound. Chunking a giant JSON blob alone repeats prefix
parse/serialize and recreates the blob cost we are removing.

Report digest decision (source: recovery canonical() +236–249)
Current v1 sorts complete canonical row strings using JS UTF16 ordering and hashes
that array. BLOBs become objects enumerating every byte as keys. Simply hashing
PK order changes v1 semantics. A scratch SQLite BINARY string sort also differs
from JS for some Unicode, and a legal BLOB can expand past a durable SQLite row
limit when serialized that way. Exact v1 needs a chunked external merge sort and
portable hash continuation, adding avoidable report machinery. Prefer explicit
contractVersion2 for typed-cell, code-owned stable-PK-order streaming digests,
with a documented old/new comparison boundary. This changes reporting, not any
semantic audit predicate. It needs root approval and consumer/test review; not an
unannounced v1 hash change. Portable SHA state already exists in replay-sha256;
reuse it, with exact input framing and persisted cursor/state, not process crypto
objects. NULL/BLOB/Unicode and all PK layouts need admitted total ordering.

A modified current metadata record with recomputed payload hash/size and COMPLETE

content framing/equality alone cannot imply logical validity. Log adjacent.

Mathematically sufficient equivalence requires BOTH:
- authenticated provenance that the exact immutable input/schema/runtime contract
  really passed independent validator P, not a caller attestation; AND
- exact typed multiset/keys equality for EVERY logical table/relationship relevant
  to P, with equivalent schema/constraints/collations/format. Target-owned controls,
  runtime permits and scratch are intentionally different and need separate exact
  validation. Existing skipped/retired or sanitized fields must be accounted for;
  equal normalized rows are not byte-for-byte equality of source SQLite pages.
Even that transfers logical P only. Source quick_check says nothing about physical
corruption/index integrity of newly constructed target B-trees. The Worker must
still run its own engine/constraint checks. Content bag sum/xor is a cryptographic
multiset commitment with its own assumptions, not literal byte equality/proof of
trusted external execution. Backup age does not prove later revocations absent.

Therefore an untrusted offline JSON receipt cannot safely remove target fullaudit.
A new trusted-verifier/signing/attestation authority would be a product/security
contract change; none is implemented or requested here. The existing CLI is a
valid complete recovery path for a Node/self-hosted target and a useful independent
qualification tool. For Durable Objects it can aid source diagnosis and work
planning; it does not justify verified200 without the required target predicates.

Recommended honest deployable direction
Reuse existing operator continuation + target freeze; implement durable independent
census/replay/subsystem stages with one fixed scratch relation, version report
serialization explicitly, and retain measured atomic SQLite table checks as such.
This is restartable recovery with bounded application units and documented engine
atoms, rather than an impossible strict per-row guarantee over SQLite internals.
No new service, signer, source certificate or runtime task/authority system.
