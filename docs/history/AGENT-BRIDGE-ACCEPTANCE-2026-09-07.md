## Evidence boundary

This matrix translates the assigned [research brief](DARKBLOOM-COMPUTE-ROOM-2026-09-07.md) into observable acceptance criteria. The six cases below are **proposed and not run**. They do not report an inference result, charge, cancellation, review verdict or human approval.

Current Room capabilities include explicit assignment/accept/start/complete transitions, durable events, credential permissions and review tied to an exact receipt. Room membership currently exposes Room-wide context; it is not a task-specific context grant. There is no Dasha execution adapter, MCP transport, unattended runner or per-tool spending grant.

The brief reports that Dasha's inspected local kit routes to polling providers but stores jobs in memory, creates a new ID per submission, removes jobs after responding, and lacks a consumer lookup/cancel or submission-idempotency contract. Billing is absent. Those findings concern the inspected local kit; the hosted service contract remains unverified. Coordinator/provider operators may see prompts.

## Six acceptance cases

| ID / trigger | Proposed expected behavior | Observable evidence required to pass |
| --- | --- | --- |
| **AC-01 — Selected context and permission.** Select two messages and one file; then change the file or request a broader route. | Before dispatch, authorize an immutable context manifest and digest, work revision, audience/provider class, route, model, output limit, deadline and any spending ceiling. Transmit only the selected content. A changed manifest or grant requires new authorization. Room access alone never grants Compute execution; keep credentials out of messages. | A local test receiver gets exactly the authorized package, with no unrelated Room text or credentials. Stored grant and outbound attempt identify their authorizer and digest. Changed-file, expired-grant and broader-route cases reject before dispatch; outbound request count stays zero. |
| **AC-02 — Duplicate submission.** Repeat the same submit after losing its response; replay Room history. | Persist an attempt before contacting Compute. Reuse its stable submission key and recover the same job. Event replay only rebuilds state. Require a verified server-side idempotency contract before enabling real submissions; Room command deduplication alone is insufficient. | Durable attempt records link one Room command/work revision/context digest to one Compute job. A fake Compute service records one job despite repeated requests. Restart and event replay add no job. Altered payload under the same key is refused. |
| **AC-03 — Unknown outcome.** Connection drops after Compute accepts, before Room receives a job/result. | Show outcome unknown and reconcile by durable submission/job identity. Do not equate timeout with failure or automatically submit again. If lookup cannot establish the outcome, retain the uncertainty and request operator resolution. | Fault-injection trace proves acceptance occurred, then response loss. After restart, status lookup recovers the original job and output; total jobs remains one. An unavailable lookup leaves the work unresolved with its last checked time and an actionable reason. |
| **AC-04 — Cancellation acknowledgment.** Request Stop while output arrives, including a late completion. | Record cancellation requested separately from acknowledged terminal execution state. Show Stopping until authoritative acknowledgment. Preserve a late completion and its provenance; never claim execution stopped or cost vanished from a local disconnect or cancel request alone. | Ordered request, acknowledgment and completion records with timestamps and job identity. Delayed acknowledgment keeps Stopping visible. A completion-before-cancellation race retains the result and truthful terminal state. Usage/cost reconciliation remains separate. |
| **AC-05 — Exact output review.** Submit output A, then replace it with B after A is reviewed. | Bind each receipt to exact output bytes/version, completion event and available actual model/build provenance. A separate reviewer retrieves those bytes. Review of A cannot approve B; record missing provenance as unknown. Apply the work's required owner-decision gate afterward. | Fetchable artifact hash matches the receipt. Review records reference its exact completion event/version. B has no inherited review or decision; stale review references are rejected. Current next step requests B's review and leaves required human approval pending. |
| **AC-06 — Unknown usage/cost.** Completion lacks token usage, final cost or settlement data. | Preserve unknown values explicitly. Distinguish estimates, authorization ceilings, reservations, reported usage and final charges. Never display missing cost as zero or treat a provider report as settled payment. No paid fallback beyond the grant. | Receipt/UI fixtures retain null/unknown with measurement source and freshness where available. A late usage report updates provenance without inventing settlement. A route exceeding the grant is rejected before dispatch. |
