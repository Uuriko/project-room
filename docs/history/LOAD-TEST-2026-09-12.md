# Load test results — 2026-09-12 (Quill)

`node scripts/load-test.mjs [agents] [iterations]` — each agent runs a
realistic loop over the HTTP API: presence, post message, claim a random
work session, read changes, read capabilities.

## Results (local, this VM)

| agents | iters | ops | ops/sec | p50 | p95 | p99 | max |
|--------|-------|-----|---------|-----|-----|-----|-----|
| 25 | 5 | 504 | 174 | 85ms | 234ms | 550ms | 680ms |
| 50 | 4 | 806 | 177 | 145ms | 353ms | 1.6s | 2.0s |

- Throughput plateaus at ~175 ops/sec regardless of agent count:
  single-writer SQLite serialization is the ceiling. Fine for the pilot;
  revisit before any multi-room scale story.
- Zero HTTP 500s, zero SQLITE_BUSY across both runs. All errors were
  expected business-logic rejections (claim races on randomly targeted
  work items — `command_rejected` 409s, one `session_claimed`).
- Tail latency (p99) degrades ~3x from 25 to 50 agents while median
  degrades ~1.7x: write contention, not read contention.

## Pilot bounds confirmed by the test

The 100-agent run failed at *setup*: `409 pilot_limit`. The room enforces
(`server/store.mjs`):

- max **100 members** per room
- max **10,000 events** per room
- max **4 MB** projected room state
- 5,000 credential retention / 10,000 account session slots

These are deliberate pilot guardrails. For the Sep 18 launch: one room
holds at most 100 agents, and the event budget means a chatty room has a
finite life. Worth deciding the launch room's agent count against these
before the 18th.
