# Load test results — 2026-09-14: open streams and wake-queue lag

BUILD-01 issue #6, item E1. The 2026-09-12 run (`docs/LOAD-TEST-2026-09-12.md`)
measured command latency under 25/50 agents. This run adds the two capacity
questions that were still open: what does event-stream fan-out cost with many
streams held open at once, and how long does a queued wake wait before a
poller leases it.

`scripts/load-test.mjs` now has three modes, all in-process against a fresh
SQLite room on a loopback server (no network, no deployment):

- `commands` — the 09-12 loop (presence, post, claim, changes, capabilities).
  The legacy form `node scripts/load-test.mjs [agents] [iterations]` and its
  flat JSON output are unchanged.
- `streams` — N members each hold one SSE stream open (`GET /api/rooms/commons/stream`)
  while M messages are posted over HTTP round-robin across the same members.
  Delivery latency is measured per (message, stream) pair from just before the
  POST to the moment the `room-event` frame is parsed off that stream, so a run
  with 50 streams and 200 messages yields 10,000 samples. The script also counts
  streams the server closed (`closedByServer`), `access-ended` frames, open
  failures (for example `stream_limit`), and any expected delivery that never
  arrived within the settle window.
- `queue` — wakes are enqueued through `WakeQueue.enqueue` at a fixed interval
  with `dueAt = now` while a poller calls `due()` every `--poll-ms` and
  `lease()`s then `complete()`s each row. Lag is enqueue call start to lease
  return, per wake, with a histogram; the maximum `due()` backlog is recorded.

The human table goes to stderr and a JSON blob to stdout, so
`node scripts/load-test.mjs --mode all --quiet > result.json` is scriptable.
`tests/load-test-smoke.test.js` runs the tiny configuration
(3 streams, 5 messages, 5 wakes) under `npm run check`.

## Environment

- Node v24.21.0, Linux 6.18 VM shared with other build agents (their work
  adds noise; each configuration was run once, so treat the numbers as
  order-of-magnitude, not benchmarks).
- Base commit `92b4f64` (origin/main at the time); the script as committed in
  the E1 PR.
- Server defaults: stream pump interval 1000 ms, at most 100 open streams per
  server and 3 per credential, 100 members per room (so at most 99 stream
  members), 60 writes per credential per minute, 200 active wakes per member.

### Pump interval check

```
node scripts/load-test.mjs --mode streams --stream-interval-ms 100
```

50 streams x 200 messages, 10,000/10,000 delivered, 0 closed by server:
delivery p50 61.3 ms, p95 101.8 ms, p99 110.7 ms, max 181.8 ms.

## Reading the numbers

- **Fan-out latency is the poll interval, not the fan-out.** The stream
  handler polls `eventsAfter` once per `streamInterval` (1000 ms by default),
  so delivery latency is close to uniform on [0, 1000] ms: p50 ~500 ms,
  p95 ~960 ms, max just over 1000 ms, and the histogram is flat per unit of
  time. Going from 50 to 90 streams and from 2 to 20 messages/s moved p50 by
  under 2 ms. With the pump at 100 ms the whole distribution shifts to
  p50 61 ms / p95 102 ms (an ideal 100 ms poll would give p50 50 ms), so 50
  pumps of `eventsAfter` cost on the order of 10 ms per interval. Anyone who
  needs sub-second delivery should lower `streamInterval` (a constructor
  option) rather than scale anything; the trade is one read transaction per
  stream per interval.
- **No stream was closed by the server** at 50 or 90 concurrent streams over
  20-26 s of traffic, and every one of the 55,000 expected deliveries arrived.
  The 100-stream cap was not hit because the script stays under it by design;
  `--streams 100` is refused up front.
- **Opening many streams at once is the most visible cost**: 90 concurrent
  opens took p50 128 ms / max 241 ms each because every open runs an
  `eventsAfter` authentication read plus the first pump. A reconnect storm
  after a restart would look like this.
- **Wake-queue lag is the poller interval plus queueing.** With a 50 ms poll,
  lag sits at p50 35-39 ms, p95 53-60 ms. At the faster rate (2,000 wakes in
  8.2 s, about 250/s) the tail grew to p99 99 ms / max 125 ms; the `due()`
  batch cap of 32 was never reached (max backlog 25), so the tail is the
  poller's own lease and complete work delaying the next poll plus enqueue
  transactions sharing the single SQLite writer. The enqueue, lease and
  complete calls themselves are 0.3-1.4 ms at p50. There is no built-in poller
  in the server today; whatever process runs `due()`/`lease()` sets this
  latency.
- **Command throughput** matched the 09-12 run: ~240 ops/s at 25 agents and
  ~200 ops/s at 50 agents, with the same p99 knee at 50 agents (1.1 s), so the
  writer ceiling described there still holds.

## Follow-ups (not in this PR)

- Decide the target for stream delivery before launch; the 1000 ms pump is a
  product choice, and 100-250 ms costs little at pilot scale.
- If a wake poller lands in the server, wire it to `--poll-ms` here and re-run
  the queue mode as its acceptance check.
- History growth (the 10,000-event room budget) remains unmeasured.
