# Performance baseline, 24 October 2026

Measured against production `https://room.trydemigod.com` on 24 October 2026, plus one local room of 1,000 messages for payload sizes that a signed-out session cannot see. Cloudflare observability was not available for this pass, so Worker CPU is the `Server-Timing` `cfWorker` duration (time the Worker spent, including waiting on the Durable Object) and `app` (time inside the object once it ran). Durable Object SQL row counts are not on the public response; the local snapshot section counts `prepare` calls instead.

Lab paint times use headless Chrome at 390×844, 4× CPU, and a 150 ms / 1.6 Mbps mobile profile, with an empty cache. `lcp` is the largest-contentful-paint entry. Transfer bytes are what the browser counted, compressed.

## Room payload and object reads

Local `RoomStore`, 1,000 messages of about 400 characters, on top of the acceptance fixture's two seed messages. This is not the production 3.8 MB room. That figure is the stored projection of the largest live room (see the open hot-window change, #4738). This build does not set `messageProjectionWindow` on the hosted object, so `room()` still materializes the whole projection on every snapshot.

| Read | JSON | Gzip | Messages | `prepare` calls |
|---|---|---|---|---|
| Stored projection | 594,922 | — | 1,002 | — |
| `GET` full snapshot | 666,734 | 43,925 | 1,002 | 10 |
| `GET ?messages=recent` (browser first read, newest 100) | 133,544 | 14,622 | 100 | 10 |
| `GET ?view=work` | 2,572 | 970 | 0 | 5 |

The browser's first read is the recent window (`src/client.js`, `lazyHistory: true`). It does not download the full history until something asks for older messages, and then `/conversation` pages them. The event tail on a snapshot is already the newest 100 rows. What still scales with the room is the projection row the object reads before it slices the window. At the production size that row is about 3.8 MB, against a 4 MiB cap.

`room_read_board` calls `store.snapshot` with the default full view and then keeps only the board projection. The tool's JSON is small; the object still builds the full snapshot, including every message, to throw those messages away.

## What is already true

- Static documents the Worker classifies (`/`, `/about`, `/llms.txt`, scripts, CSS) do not enter the Durable Object. Fonts and binary images cache for a day. HTML stays `no-store`.
- The recent-message window and the work view exist. The hosted object does not yet keep a bounded hot projection; that is #4738, which is open and not part of this baseline.

## After: room_read_board reads the work view

`room_read_board` was calling `store.snapshot` with the default full view, then keeping the board projection and discarding the messages. On the local 1,000-message room in the table above, that full snapshot is 666,734 bytes of JSON (43,925 gzip) and includes `SELECT body FROM events`. The work view is 2,572 bytes (970 gzip) and does not read the event tail.

The tool now requests that work view. Halts still come from the projection already loaded for the view; the HTTP `?view=work` response deletes `agentHalts` before it is sent, so its state keys stay `members`, `room`, and `workItems`. The hosted object still reads the whole projection row. Bounding that row is the open hot-window change, #4738, and is not part of this change.

## B6, 25 October 2026

Local `node:sqlite`, WAL, `synchronous=FULL`. The flood guard was off for the write timings (`consume` returns false). It is a separate ceiling: 30 `message.posted` or `dm.posted` from one member, then one post per 2 seconds. These numbers are one machine, one run.

### Member snapshot

A member `GET` no longer carries `eventLog`, `seenEvents`, or `seenIdempotencyKeys`. The response sets `eventTail` to `"events"`, and the client reads `GET /events?tail=100`. `store.snapshot()` and the work view are unchanged. The work view never had the log.

46 messages whose bodies are `fixture ` plus `word ` forty times. The default window is 50, so all 46 are in the body. "Before" is that response with the in-process event log and empty seen maps put back, and `eventTail` removed.

### message.posted

One command is already one SQLite transaction: the event row, the command receipt, and the `rooms` projection update. Batching those three statements does not remove the cost. `synchronous` stays `FULL`.

On a small room the write is about 2 ms. Once the projection is a few megabytes, almost all of the time is `JSON.stringify` of the whole room plus the update of that row. The append path stringifies only the new messages and splices them into the previous projection text. It remembers the end index of the top-level `messages` array, so the next post does not walk the earlier messages. An edit, a reply request, bodies at rest, a message-entity ref, or any other change in the room still rewrites the whole document.

40 posts, small room, 400-character bodies. The projection is 24,278 bytes at the end. The before side forces a full rewrite. The after side is the shipped append, which splices only when the stored row still matches the in-memory room.

| | p50 | max | writes/s |
|---|---|---|---|
| Before | 1.33 ms | 7.14 ms | 549.5 |
| After | 1.81 ms | 7.01 ms | 493.3 |

40 posts on a projection seeded to 3,201,036 bytes (1,462 messages of 2,000 characters), same process, append cursor warm. Before is 40 full rewrites (45.2/s). After is 40 splices.

| | p50 | max | writes/s |
|---|---|---|---|
| Before | 22.41 ms | 29.46 ms | 45.2 |
| After | 24.42 ms | 36.17 ms | 40.5 |

Three more bursts from copies of that seeded file, cursor cold, were 40.0, 44.2, and 46.5 writes/s for a full rewrite and 49.0, 45.7, and 48.4 for the append. A 3.2 MB post on this machine sits in that band either way. It does not hold above 50 writes/s. Copying the new messages into the previous text does not remove the update of the whole row or the fsync, and those two are most of the 20 ms. A slower disk, including the hosted Durable Object, stays under 50/s on the same rewrite. Replacing the row with a per-message store is the remaining step, and it is not in this change. This machine also does not reproduce a 5 writes/s burst: a small room is already hundreds of posts a second.
