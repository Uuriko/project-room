PROJECT ROOM: DISCORD QUALITY AUDIT AND PRODUCT CHECKLIST
2026-10-08 UTC — research and first implementation checkpoint

OUTCOME TO AIM FOR
A room opens into a legible, responsive shared conversation. People and friends
can talk naturally, ask one room assistant for help, and inspect useful results.
The swarm stays behind that assistant. Agent tools remain fast and direct through
API/MCP/CLI; technical details appear in Advanced rather than dominating human chat.

This is an audit framework, not a claim of Discord parity. Desktop/browser text
chat quality is the first target. Full Discord parity would also require voice,
video, screenshare, rich media, communities, moderation, notifications, offline
behavior and mature distribution. Do not add all of those to fix today's clutter.
Do not treat the absence of a feature as permission to add it without a user need.

WHAT DISCORD TEACHES US
1. Persistent regions give navigation a stable home. Its keyboard architecture
   treats server list, channel list, messages and people as distinct regions [S1].
   Adopt predictable focus and navigation boundaries, not its React internals.
2. Keyboard access covers the whole app, with message actions and section jumps;
   shortcuts supplement discoverable controls [S2, S3]. Our command palette should
   be an accelerator, not the only way to find ordinary human actions.
3. Current design guidance uses consistent shape language and less crowded chat
   controls. Its August2026 revision keeps frequent actions near the composer and
   puts less frequent actions in a menu [S4]. Use one icon weight and radius scale;
   keep people identifiable and room/work objects visually distinct.
4. Its mobile redesign reported faster startup, less data and cached recent
   conversations [S5]. The useful lesson is keeping conversation data close and
   avoiding reloads, not blindly adopting its cache counts or copying old tabs.
5. Recent performance work includes changing startup payload order and smoothing
   navigation [S6, S7]. Profile our critical path before adding infrastructure.
6. Attachment retries and upload resumption improve reliability as well as speed
   [S8]. A quick-looking send that duplicates work is a regression.
7. Settings organization and search reduce hunt time [S9]. Project Room's human
   profile, account security and room settings should have obvious distinct homes.
8. Heuristic evaluation demands visible status, familiar controls, recovery and
   minimal competing information [S10]. Removing labels alone is not simplicity.
9. Accessibility includes target size, unobscured focus, authentication assistance,
   and alternatives to drag gestures [S11]. Icons still need accessible names.
10. Web Vitals supplies measurable loading, interaction and stability criteria
    [S12]. A clean screenshot alone is not a performance result.

ELEMENT DECISION RULE
For each visible element, record: user goal; frequency; state/permission; duplicate
entry points; number of actions; space used; failure behavior; accessible name;
keyboard/touch route; whether it belongs to a human or agent audience.
Then choose KEEP, REMOVE, COMBINE, MOVE, REWORD, REPAIR or ADD. Never hide an error,
consent boundary, permission consequence or pending effect merely to reduce words.
An icon is justified when recognizable and named; unfamiliar actions keep labels.

Google path in an unconfigured preview. Personal Google return remains unverified.
P1: Logo and coherent entrance; compact header; one composer; one quiet assistant
status. Reduce common-action clicks, retain private/public audience cues.
P1: Measure message send, thread/room switches, search and long-list scrolling.
P2: Consolidate overlapping update/activity/result navigation after a complete
feature inventory and acceptance of replacement routes. Reconcile Claude's stack.
P2: Unify settings, icons, menu spacing, skeleton/error/empty states and typography.
P3: Richer avatars/room imagery and broader social features, only after chat feels

RELEASE ACCEPTANCE TARGETS — OUR PROPOSED TARGETS, NOT DISCORD MEASUREMENTS
- Signup: two essential email/password button clicks before a usable personal room;
  optional personalization later. Google: one provider action plus provider-required
  consent. Never bypass a required security/consent step to meet a click target.
- Common chat: focus, type, Enter; reply, attach, reaction entry each directly reachable
  in one activation where practical. Confirmation needed only for material effects.
- Navigation: search/palette open in one activation; switching retains drafts,
  scroll and audience. Esc dismisses the nearest temporary layer before the room.
- Field p75 targets: LCP<=2.5s, INP<=200ms, CLS<=0.1 from Web Vitals [S12].
- Proposed local interaction targets: cached navigation feedback within100ms,
  visible pending-send feedback within100ms, no regular>50ms main-thread task while
  typing. These are future measurement budgets, not results from this CSS patch.
- Same-origin/profile workloads: collect at least30 repetitions, report median and
  p95, capture cold and warm separately, record machine/runtime/network/settings.
  Do not compare a fast local server with Discord's live backend as a fair benchmark.
- Responsive:320/390/768/1280/1440px; browser zoom and text200%; light/dark;
  keyboard/coarse pointer; Chromium and actual Mac WebKit. No overlap/hidden focus.
- Agent path: direct tool operations, stable request IDs, exact retry arguments,
  genuine status receipts and a recovery path. Never infer success from a spinner.

before screenshot/trace, severity, chosen decision, code owner, strongest existing
behavioral test, after evidence and release status. P0=data/auth/access failure;
P1=frequent workflow friction; P2=secondary polish; P3=optional breadth.

USER JOURNEYS THAT MUST FEEL GOOD
A. New human: logo -> signup -> usable personal chat -> invite friend -> friend joins.
B. Returning human: provider/password -> prior room -> scroll/draft restored -> reply.
C. Friends working: casual chat -> shared prompt -> one assistant status -> useful result.
D. Disconnected assistant: clear compact state -> connect -> preserve conversation.
E. Attach: one entry activation -> choose file -> staged preview -> send -> real download.
F. Busy timeline: read history while20 new messages arrive -> keep reading position.
G. Offline/reconnect: write draft -> failed send -> reconnect -> exact retry, one receipt.
H. Lost mutation response: review actual outcome -> retry original ID -> no duplicate work.
I. Permission change: private draft stays private; revoked controls explain refusal.
J. Keyboard only: login -> chat -> search -> message action -> Escape -> composer.
K. Native provider: cancel, retry, consent, return, expired callback, full relaunch.
L. New agent: identity -> saved credentials -> room -> direct tool work -> human result.
M. Large room: 10k messages, long names, attachments and concurrent writers -> bounded UI.
N. Recovery: stale invite, expired session, changed terms and inaccessible result.
