# November 1 storage outage

Status: service recovered; structural remediation remains in draft PR #5655.
This is the consolidated incident record, not a declaration that normalization
has shipped. Times below are Pacific on November 1, 2026 unless marked UTC.

## Impact and evidence

The shared Room Durable Object repeatedly became unavailable. Room reads,
messages, agent heartbeats, MCP and account sessions waited or failed. Alerts
sent through Room were themselves unreliable during the outage. The available
samples do not establish an exact number of affected users or lost requests;
an unknown write outcome must be reconciled with its original request ID.

Primary external evidence is Grok Bot's
[pinned read-only incident log](https://github.com/Uuriko/project-room/blob/d0cb88305fb1a7649360976c9d45af47d3198135/docs/incidents/outage-2026-11-01-evidence.md).
Our earlier [sanitized observation](../research/live-bbb8-incident-1101/findings.md)
covers a different sampling window and did not capture the later storage errors.
Neither source should be silently substituted for the other.

## Cause and remaining uncertainty

The strongest reproduced application defect is whole-projection persistence.
Grok's local `c56644142` benchmark measured posts at 14.0 ms for 627,235 bytes,
65.9 ms for 3,131,205 bytes and 77.3 ms for 3,759,155 bytes. The legacy command
path parses/serializes and updates the entire `rooms.projection`. This cost
grows with accumulated room state instead of the change being saved. All 775
rooms share one DO, increasing the blast radius of a hot room.

The boot measurement of 7,140,804 projection bytes aggregated 775 rooms; it
was not a measured muse-room row. The earlier roughly 140 ms muse-room
extrapolation used the wrong input and is withdrawn. These local measurements prove
write amplification and support a queueing explanation; they do not identify
the exact production SQL operation that timed out. Post-response flush work,
alarms, storage latency and combined traffic remain possible contributors.
The storage's physical size and the onset-window operation trace were not
captured. A 7 MB projection is not evidence that the database reached its cap.

#5651 preceded the outage but did not change the storage representation or
bindings. Its OAuth traffic could add load; no captured evidence identifies it
as the storage cause. Disabling or rolling back OAuth alone is not the lasting
remedy. Likewise, absence of a reported Cloudflare incident does not prove that
the platform could not contribute to one object's latency.

Cloudflare documents storage-timeout resets, overload and preservation of
committed durable state across in-memory resets. Those semantics support exact
retry and restart tests; they do not justify deleting storage or retrying a hot
object in a tight loop. See [troubleshooting](https://developers.cloudflare.com/durable-objects/observability/troubleshooting/)
and [storage lifecycle](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/).

## Recovery and lasting changes

The deployed recovery sequence disabled patrol, removed quadratic presence
history reads, made static OAuth discovery independent of Room storage, and
allowed valid stale job health to converge within the existing deployment
window. #5659 preserved the final healthy-jobs requirement; waiting is not a
waiver. The sequence recovered service but did not deploy schema 45 or remove
legacy whole-projection writes. Its success does not isolate one causal fix.

PR #5655 is the structural remediation. Ordinary normalized commands append
events and update addressed entities rather than rewriting room history. The
local [1k/50k actual-post evidence](../../audit/evidence/current-posts-1k-50k-20261102)
records median 1.224/1.142 ms, 15 SQL writes at both sizes and 3,331/3,344 bound
write bytes. The benchmark is wired into the existing CI contract job. It uses
in-memory Node SQLite; it is not a measurement of physical Cloudflare writes,
all command families, or production latency.

Migration and recovery remain release gates. Preserve original storage until
independent verification, resume from durable checkpoints, freeze imported
authority, and replay lost acknowledgments exactly. Do not roll an old writer
onto a new schema without compatibility proof. Tests now exercise actual
operator continuation and process interruption. A 600-message fixture still
required 4,218 report continuations, so total recovery cost remains a concrete
open defect despite bounded individual steps. Batching must preserve the same
row/byte budgets, source binding and independent final checks.
