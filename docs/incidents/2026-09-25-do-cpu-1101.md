# Incident: 2026-09-25 Durable Object CPU reset (1101)

The room Durable Object exceeded its CPU time limit and was reset. DO-backed
routes returned 500/1101. The write-up in the tree is
`docs/INCIDENT-1101-RUNBOOK.md`, first written from this outage and
root-caused the same day. `cloudflare/room.mjs` records the same date: `/api/version`
1101'd with everything else, so deploy verification could not see what was
deployed.

## Timeline

The repository records the calendar date and the same-day root cause. It
does not record clocks for the four steps below.

### Detect

Not recorded (PT). The observed signature is the 2026-09-25 1101 pattern in
`docs/INCIDENT-1101-RUNBOOK.md` and `scripts/probe-prod-lib.mjs`.

### Start

Not recorded (PT).

### Mitigate

Not recorded (PT). The mitigation was a settings-only change of the Durable
Object CPU budget from 1000 ms to 30000 ms. It did not change
`sourceRevision`, so `/api/version` alone could not identify it.

### Resolve

Not recorded (PT). The runbook says the original object state came back
after the budget change, and the outage was root-caused the same day.

## Cause

The Cloudflare tail showed `Durable Object exceeded its CPU time limit and was reset`.
The owning script's CPU budget was 1000 ms. `docs/ROOM-DEPLOYMENT.md` keeps
`env.production.limits.cpu_ms` at 30000 because that 1000 ms budget caused
repeated CPU resets and HTTP 500/1101 on this date. The entry Worker's own
1000 ms forwarding budget is a separate limit.

The runbook treats constructor throws, memory pressure, and cron overlap as
other candidates for a later 1101, not as the cause shown for this window.

## Why detection took this long

`/api/version` is forwarded to the Durable Object. While the object was
resetting it returned 1101 with the other DO-backed routes, so the deployed
revision was hidden. The comment on `GET /api/version/worker` in
`cloudflare/room.mjs` is the record of that gap.

Job heartbeats are written through the same object they monitor. A quiet
heartbeat is not health. `/api/health/jobs` still answered, through the
Worker's catch around the DO RPC, so the Worker was up while the object
was not. That split is the `do-rpc-fail` verdict in `scripts/probe-prod-lib.mjs`.

## What users and agents saw

From `docs/INCIDENT-1101-RUNBOOK.md`:

1. DO-backed routes (`/`, `/api/version`, `/api/health`, `/join`, room APIs) returned 500/1101.
2. `/api/health/jobs` still answered a clean 503 JSON response. The body showed the Worker was running and the DO RPC had failed.
3. `getdasha.com/room` answered 301. That shows the edge route answered. It does not show that the Room Worker was healthy.

The current Worker maps a Durable Object failure on `/api/version` to 503
`room_unavailable` and does not put the platform error in the body.
`/api/version/worker` answers from the Worker with `servedBy: "worker"` and
does not call `getByName`.
